### 2. [Investigar] ¿Cuál es la historia de gRPC: desde Stubby (el sistema RPC interno de Google, 2001) hasta gRPC open-source (2015)? ¿Por qué Google finalmente decidió open-sourcearlo y cómo influyó HTTP/2 en la decisión?

**Respuesta**: Google usó un sistema RPC propietario llamado **Stubby** internamente desde ~2001 para comunicación entre sus cientos de miles de microservicios. Stubby usaba Protocol Buffers (creado en 2001) y corría sobre una capa de transporte custom (no HTTP). En 2015, con HTTP/2 estandarizado, Google vio la oportunidad de reescribir Stubby sobre HTTP/2 como transporte estándar (en lugar de transporte propietario). Esto permitió que gRPC funcionara en infraestructura HTTP estándar (load balancers, proxies, firewalls), haciéndolo viable para open-source. gRPC se anunció en febrero 2015 como evolución de Stubby + HTTP/2. La decisión estratégica fue: open-sourcear la tecnología interna de Google para competir contra REST en el espacio de microservicios y establecer protobuf como estándar de serialización.

**Por qué**: La historia está documentada por Google Cloud (grpc.io/about) y en charlas de Louis Ryan (Google, co-creador de gRPC) en gRPC Conf 2017. Stubby manejaba billones de RPCs por segundo internamente. La migración a gRPC no fue solo open-source: Google mismo migró sus servicios internos de Stubby a gRPC. gRPC es hoy el estándar de comunicación en Google Cloud (Cloud Spanner, Cloud Bigtable, Cloud Pub/Sub), en CNCF (graduado en 2018), y en proyectos como Kubernetes (parcialmente) y Envoy. La lección: gRPC no es una startup creando algo nuevo — es Google productizando 15 años de experiencia en RPC a escala planetaria.

### 3. [Investigar] Compará Protocol Buffers, Apache Thrift (Facebook, 2007), Apache Avro (Hadoop ecosystem), y Cap'n Proto (ex-Google engineer). ¿Cuáles son las diferencias técnicas clave y cuál domina en qué ecosistema?

**Respuesta**: **(1) Protocol Buffers** (Google, 2001, público 2008): binario compacto, schema-first, codegen para 12+ lenguajes. Dominante en gRPC y Google Cloud. Serialización sin parsing (acceso directo a campos en memoria). **(2) Apache Thrift** (Facebook, 2007): soporta 20+ lenguajes, múltiples protocolos de transporte (no solo binario), incluye server framework (no solo serialización). Dominante en sistemas legacy de Facebook y algunas empresas enterprise (pero Facebook migró a GraphQL + protobuf internamente). **(3) Apache Avro** (Doug Cutting, Hadoop): schema embebido en los datos (no requiere codegen — el schema viaja con los datos), orientado a big data y streaming (Kafka). Dominante en ecosistema Hadoop/Kafka. **(4) Cap'n Proto** (Kenton Varda, ex-Google, autor de Protobuf v2): serialización zero-copy (los datos en wire son idénticos a la representación en memoria), más rápido que protobuf. Nicho en sistemas de ultra-baja latencia (Cloudflare Workers).

**Por qué**: La elección depende del ecosistema: gRPC → protobuf (es la única opción nativa). Kafka → Avro (Confluent Schema Registry). Sistemas multi-lenguaje legacy → Thrift. Ultra-latencia → Cap'n Proto. Para TaskFlow con gRPC, protobuf es obligatorio. La diferencia técnica clave: protobuf usa binary encoding con field tags numéricos (similar a lo que enseña la clase); Avro usa schema evolution sin field tags (más flexible para data lakes); Cap'n Proto usa zero-copy (no serializa/deserializa, solo castea punteros). La comparativa de performance (Kenton Varda, capnproto.org) muestra Cap'n Proto ~2-5x más rápido que protobuf en serialización, pero protobuf es ~10-200x más rápido que JSON.

### 4. [Investigar] ¿Qué es el concepto de "Global Object Identification" (Node interface) en GraphQL y cómo se relaciona con la normalización de caché en clientes como Apollo y Relay? ¿Por qué es una de las características más infravaloradas de GraphQL?

**Respuesta**: Global Object Identification es un patrón definido en la especificación Relay de GraphQL: cada tipo que implementa la interfaz `Node` debe tener un campo `id` que es globalmente único en toda la API (no solo único dentro de su tipo). Esto permite que cualquier objeto se refetchée con `node(id: "VXNlcjox")`. Relación con caché: Apollo Client y Relay normalizan la caché usando estos IDs globales como keys. Si dos queries distintas devuelven el mismo usuario, el cliente lo detecta porque comparten `id` global y lo almacenan una sola vez (normalización). Sin IDs globales, el cliente no puede saber si `{id: "1"}` de una query y `{id: "1"}` de otra son el mismo objeto o no.

**Por qué**: La especificación Relay (relay.dev/docs/guides/graphql-server-specification/) define `Node` y `Mutation.input` como estándares que todo servidor GraphQL debería implementar. La mayoría de tutoriales y cursos de GraphQL ignoran esto, enfocándose solo en queries y mutations. Pero en producción, la normalización de caché es lo que hace que Apollo Client sea eficiente: evita requests duplicados, actualiza la UI automáticamente cuando una mutation retorna el mismo objeto, y mantiene consistencia. La implementación en el servidor: cada tipo debe tener `id: ID!` (no Int, no String — ID es un tipo especial), y debe ser globalmente único, típicamente codificado como base64 del nombre del tipo y el ID local: `base64("User:1")` → `"VXNlcjox"`.

### 5. [Conectar] ¿Cómo se relaciona el concepto de "deadline propagation" en gRPC con los timeouts en REST? ¿Por qué gRPC tiene una ventaja arquitectónica aquí?

**Respuesta**: En gRPC, cada RPC lleva un deadline (tiempo máximo para completarse). Este deadline se propaga automáticamente a través de todas las llamadas subsecuentes: si el servicio A llama a B con deadline de 500ms, y B llama a C, B pasa el deadline restante a C (ej. 300ms después de su propio procesamiento). Esto permite que todo el árbol de llamadas se cancele ordenadamente cuando el deadline se cumple, evitando trabajo inútil en servicios downstream. En REST, los timeouts son típicamente configuraciones locales en cada servicio (connection timeout, read timeout) sin propagación — el servicio B puede seguir trabajando aunque A ya hizo timeout, desperdiciando recursos.

**Por qué**: La propagación de deadlines es una de las características más poderosas y menos mencionadas de gRPC. Está documentada en gRPC's "Deadlines" (grpc.io/docs/guides/deadlines/). Jeff Dean (Google) menciona en "Achieving Rapid Response Times in Large-Scale Services" que la propagación de deadlines es crítica para latencia tail en sistemas distribuidos — sin ella, los timeouts en cascada pueden causar avalanchas. En REST, la alternativa es usar headers como `Timeout: 500` o `X-Request-Deadline`, pero no son estándar y la mayoría de frameworks REST no los propagan automáticamente. Esto da a gRPC una ventaja real en arquitecturas de microservicios profundos.

### 6. [Conectar] ¿Cómo se comparan Apollo Federation y Schema Stitching con el patrón API Gateway (BFF) en REST? ¿Son soluciones al mismo problema?

**Respuesta**: Son soluciones al mismo problema (composición de datos de múltiples servicios) pero en paradigmas distintos. **Apollo Federation**: múltiples servicios GraphQL definen sub-schemas que un gateway federado compone en un supergraph. Cada servicio resuelve sus propios tipos y puede extender tipos de otros servicios via `@key` y `@external`. **Schema Stitching**: similar pero más manual — el gateway literalmente "stitchea" schemas GraphQL de diferentes servicios. **API Gateway BFF (Backend for Frontend) en REST**: un servicio intermediario que hace múltiples llamadas REST a servicios downstream y compone la respuesta. Diferencia clave: Federation es declarativa (los servicios declaran sus relaciones en el schema); BFF es imperativa (el desarrollador escribe código de composición manual).

**Por qué**: Apollo Federation fue creado por Apollo (Meteor Development Group) en 2019 como respuesta a la necesidad de Netflix y otras empresas de escalar GraphQL en múltiples equipos. Netflix presentó su experiencia en "Federated GraphQL at Netflix" (GraphQL Summit 2019). El BFF pattern fue popularizado por Sam Newman en "Pattern: Backends For Frontends" (2015). La elección: si ya usás GraphQL, Federation permite que múltiples equipos sean dueños de partes del schema sin coordinación central. Si usás REST, BFF es el patrón probado para evitar que el frontend haga 20 requests. Son análogos funcionales en sus respectivos ecosistemas.

### 7. [Conectar] ¿Cómo se relaciona el patrón DataLoader de GraphQL (batching y caching por request) con el pre-caching de recursos relacionados en HATEOAS? ¿Atacan el mismo problema de "N+1 en el servidor"?

**Respuesta**: Atacan el mismo problema desde ángulos complementarios. **DataLoader**: batching y caching en el servidor durante una sola ejecución de query GraphQL. Evita que N resolvers individuales hagan N queries; en su lugar, una sola batch query. **HATEOAS con `_embedded`**: pre-caching de recursos relacionados en la respuesta (el servidor incluye los datos de `user` y `comments` embebidos en la respuesta de `task`). Ambos resuelven "N+1 en el servidor" pero en momentos diferentes: DataLoader optimiza la ejecución de queries del servidor (reduce queries a DB); HATEOAS con embedding optimiza las requests del cliente (el cliente recibe datos relacionados sin requests adicionales). Son complementarios: podrías tener una API HATEOAS donde el assembler usa DataLoader internamente para construir los `_embedded`.

**Por qué**: El problema N+1 es ubicuo: en REST, si el cliente necesita tareas + usuarios asignados, hace GET /tasks (1 request) y luego N requests a /users/{id} para cada tarea (N requests) → N+1 requests HTTP. En GraphQL, el servidor hace 1 query por todas las tareas + N queries por los usuarios de cada tarea → N+1 queries DB. DataLoader resuelve el segundo caso (servidor); HATEOAS con `_embedded` o `?expand=user` resuelve el primero (cliente). La solución completa: REST con sparse fieldsets + embed/expand parameters + el servidor usando batching de queries internamente (como Hibernate `JOIN FETCH`). La clase menciona referencing vs embedding justamente en este contexto.

### 8. [Cuestionar] ¿Es GraphQL una "bala de plata" o sufre de "death by a thousand cuts" (muerte por mil cortes) en producción? ¿Qué problemas reportan empresas que lo adoptaron a gran escala?

**Respuesta**: Empresas reportan problemas significativos: **(1) Performance impredecible**: una query GraphQL puede ser trivial o monstruosa (profundidad 10, ancho 50) — sin `maxDepth` y cost analysis, es un DoS vector. **(2) Caching difícil**: todo es POST, no hay GET cacheable — se requiere persisted queries, Apollo cache, o CDN configuraciones especiales. **(3) N+1 endémico**: sin DataLoader en cada resolver, la performance colapsa. **(4) Logging y monitoreo complejo**: un error en una parte de la query no es un status code HTTP — es un array de errores parciales que requiere instrumentación especial. **(5) Autorización granular**: en REST, `@PreAuthorize` por endpoint es simple; en GraphQL, necesitás field-level auth. **(6) File upload**: GraphQL no lo soporta nativamente (requiere multipart spec). Empresas como Airbnb y PayPal reportaron migraciones parciales DE GraphQL A REST para algunos casos de uso.

**Por qué**: El "death by a thousand cuts" es un término usado por Sashko Stubailo (Apollo) en 2019 para describir los dolores acumulativos de GraphQL a escala. Airbnb presentó "Migrating from GraphQL to REST" (GraphQL Summit 2019) para ciertos servicios internos donde REST era más adecuado. La lección: GraphQL es excelente en la capa de presentación (BFF) pero peligroso si se expone directamente a clientes sin restricciones (depth limiting, cost analysis, rate limiting por query complexity). Para TaskFlow, si se expone GraphQL, implementar `graphql-depth-limit` y `graphql-query-complexity` es tan importante como los resolvers mismos.

### 9. [Cuestionar] ¿El rendimiento superior de gRPC sobre REST se debe realmente a Protocol Buffers o a HTTP/2? Si usaras REST sobre HTTP/2 con JSON comprimido, ¿la brecha se reduciría significativamente?

**Respuesta**: La brecha se reduce pero no se cierra. El beneficio de HTTP/2 (multiplexing, header compression) aplica a ambos — REST sobre HTTP/2 también se beneficia. El beneficio de protobuf (serialización binaria compacta, sin parsing de strings) es independiente. Estudios de performance (Google, gRPC.io benchmarks, "gRPC vs REST performance" de Auth0, 2019) muestran: **(1) Latencia**: gRPC es ~7-10x más rápido que REST (JSON) en payloads pequeños-medianos. **(2) Throughput**: gRPC maneja ~2-3x más requests por segundo. **(3) Con HTTP/2 en ambos**: gRPC sigue siendo ~3-5x más rápido que REST+JSON+HTTP/2. La razón: JSON requiere serialización de strings y parsing UTF-8 incluso en HTTP/2; protobuf es copy/paste de bytes. Si REST usara protobuf (que puede, vía `Content-Type: application/protobuf`), la brecha se cerraría significativamente — pero REST+protobuf no tiene el ecosistema de codegen ni streaming nativo de gRPC.

**Por qué**: La comparación justa es REST+JSON+HTTP/1.1 vs gRPC+protobuf+HTTP/2. La comparación realista para producción actual es REST+JSON+HTTP/2 vs gRPC+protobuf+HTTP/2 (porque HTTP/2 está disponible para REST). Las mediciones de Microsoft (Azure Architecture Center) y Cloudflare muestran que para cargas de trabajo típicas de APIs (CRUD con payloads < 100KB), REST+HTTP/2 es "suficientemente rápido" y la diferencia con gRPC no justifica la complejidad adicional para la mayoría de equipos. gRPC brilla en: servicios internos de alta throughput, streaming, y payloads grandes donde protobuf reduce tamaño significativamente.

### 10. [Cuestionar] La filosofía de GraphQL es "no versionar, solo evolucionar el schema con campos nuevos y `@deprecated`". Después de 10 años de GraphQL en producción, ¿es realmente viable esta filosofía para APIs de larga vida?

**Respuesta**: Es viable pero con asteriscos. Funciona para cambios aditivos (agregar campos, tipos, arguments) y deprecaciones (marcar campos como `@deprecated`). Pero falla en cambios estructurales: **(1) Cambiar el tipo de un campo**: si `price` pasó de `Int` a `Float`, no podés — rompés clientes existentes. Tenés que crear un nuevo campo `priceV2: Float` y deprecar `price: Int`. A lo largo de años, acumulás campos legacy con nombres como `priceV2`, `priceV3`, `priceWithCurrency`, degradando la calidad del schema. **(2) Cambiar la semántica de un campo**: si `tasks` ahora requiere autenticación (antes era público), los clientes que no envían token fallan. **(3) Eliminar un tipo**: si `OldNotification` ya no existe, no podés eliminar el tipo del schema sin romper clientes que lo referencian en fragments. La solución en GraphQL es igual que REST: mantener los tipos deprecados para siempre o hacer un nuevo endpoint (en GraphQL, un nuevo schema/endpoint).

**Por qué**: Empresas con GraphQL a largo plazo (GitHub GraphQL API desde 2016, Shopify desde 2018) han tenido que lidiar con acumulación de campos deprecados. GitHub mantiene múltiples versiones de su API GraphQL internamente (cada nueva versión del schema es un nuevo "release"). La promesa de "no versionar" es cierta para evolución aditiva en plazos cortos/medios (1-3 años). Para APIs de larga vida (5-10+ años), incluso GraphQL necesita estrategias de versionado — solo que en lugar de versionar endpoints, versionás campos con sufijos o mantenés schemas legacy. La diferencia con REST es más de granularidad (campo vs endpoint) que de filosofía fundamental.
