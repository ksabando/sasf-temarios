### 2. [Investigar] ¿Por qué la comunidad de seguridad critica JWT como mecanismo de sesiones? ¿Cuáles son las alternativas y qué argumenta la "stop using JWT for sessions" crowd?

**Respuesta**: Las críticas principales de usar JWT como token de sesión: (1) **Revocación**: no podés invalidar un JWT antes de que expire naturalmente sin mantener una blacklist en el servidor — lo cual reintroduce estado y anula la ventaja stateless del JWT. (2) **Tamaño**: un JWT con múltiples claims puede tener 2KB+; se envía en cada request. Una session cookie con ID opaque es ~50 bytes. (3) **Coerción de algoritmo**: si el servidor acepta `alg: none` o permite downgrade de RS256 a HS256, un atacante puede forjar tokens. (4) **Fuga de información**: los claims son legibles por cualquiera que capture el token. La alternativa: **opaque tokens** (referencias a estado en el servidor) o **double submit cookies** (cookie con token + header CSRF). Vlad Mihalcea, Randall Degges (Okta) y el OWASP JWT Cheat Sheet documentan estas críticas.

**Por qué**: La controversia refleja un tradeoff real: JWT es excelente para **stateless service-to-service auth** (donde el servicio que valida no tiene acceso a la DB de sesiones) pero problemático para **user sessions** (donde querés poder revocar sesiones instantáneamente). Randall Degges (Okta) escribió "Please Stop Using JWTs as Session Tokens" (2018). La práctica recomendada moderna: access tokens JWT de corta duración (5-15 min) + refresh tokens opacos almacenados en servidor con capacidad de revocación. El access token se envía en cada request pero expira rápido; el refresh token permite renovación sin re-autenticación y puede ser revocado.

### 3. [Investigar] ¿Cuál es el estado actual del draft IETF `RateLimit-*` headers? ¿Qué headers propone estandarizar y cómo difieren de los headers `X-RateLimit-*` no estandarizados que usa la clase?

**Respuesta**: El draft IETF "RateLimit header fields for HTTP" (draft-ietf-httpapi-ratelimit-headers, en proceso desde 2021) propone headers estandarizados: `RateLimit-Limit` (cuota total), `RateLimit-Remaining` (restante), `RateLimit-Reset` (timestamp de reset), y `RateLimit-Policy` (política de límite). Diferencias con los `X-RateLimit-*` de la clase: (1) Sin prefijo `X-` (el IETF deprecó `X-` prefixes en RFC 6648). (2) Semántica más precisa y formalizada. (3) `RateLimit-Policy` permite al servidor comunicar exactamente qué límite se aplica y por qué (útil cuando hay múltiples políticas). El draft aún no es RFC pero está cerca de finalización (2024-2026). APIs líderes están migrando: GitHub ya soporta `RateLimit-*` (sin X-).

**Por qué**: El draft es liderado por Alexey Melnikov (IETF) con contribuciones de empresas como Fastly y Akamai. La estandarización importa porque: (1) Sin estándar, cada API inventa sus headers (`X-RateLimit-Limit`, `X-Ratelimit-Limit`, `x-ratelimit-limit`, `Rate-Limit`). (2) Los clientes no pueden parsear rate limits genéricamente. (3) Herramientas de monitoreo no pueden agregar rate limits de múltiples APIs. La clase usa `X-RateLimit-*` porque es lo que hay en el ecosistema actual, pero la dirección de la industria es migrar a `RateLimit-*` cuando el draft sea RFC. Para TaskFlow hoy: implementar ambos (los viejos `X-RateLimit-*` para compatibilidad, los nuevos `RateLimit-*` para prepararse) es una buena práctica.

### 4. [Investigar] ¿Qué es el OWASP API Security Top 10 y cómo se compara con el OWASP Web Top 10? ¿Qué vulnerabilidades son específicas de APIs y no aplican a aplicaciones web tradicionales?

**Respuesta**: El OWASP API Security Top 10 (publicado por primera vez en 2019, actualizado 2023) lista las 10 vulnerabilidades más críticas en APIs. Comparación con Web Top 10: Web Top 10 incluye injection, XSS, CSRF (enfocados en HTML/JavaScript). API Top 10 incluye: **API1:2023 Broken Object Level Authorization** (BOLA — acceder a objetos de otros usuarios por ID), **API2:2023 Broken Authentication** (JWT mal implementado), **API3:2023 Broken Object Property Level Authorization** (acceso a propiedades sensibles de objetos), **API4:2023 Unrestricted Resource Consumption** (rate limiting ausente), **API6:2023 Unrestricted Access to Sensitive Business Flows** (abuso de flujos de negocio automatizados). Vulnerabilidades específicas de APIs: BOLA (no existe en web tradicional porque las URLs de objetos no son predecibles), API3 (en APIs REST exponés campos de JSON; en web, el servidor renderiza HTML y controla qué campos muestra), API6 (bots que compran todos los items en un ecommerce — es abuso de API, no vulnerabilidad web).

**Por qué**: OWASP API Security Top 10 es mantenido por Erez Yalon y Inon Shkedy (autores de "API Security in Action"). La encuesta de 2023 identificó BOLA como la vulnerabilidad #1 porque es la más fácil de explotar y la más dañina: un atacante autenticado incrementa el ID en una URL y accede a datos de otros usuarios. La solución: autorización a nivel de objeto (ownership check) en CADA endpoint que accede por ID. Para TaskFlow, la pregunta "¿este usuario autenticado tiene permiso para ver/modificar/eliminar la tarea con ID X?" debe verificarse en el servicio, no solo en el controller. OWASP recomienda usar un framework de autorización centralizado (Spring Security `@PreAuthorize` con ownership check).

### 5. [Conectar] ¿Cómo se relaciona el algoritmo Token Bucket (enseñado en clase) con el Generic Cell Rate Algorithm (GCRA) utilizado en redes de telecomunicaciones? ¿Cuál es la base matemática común?

**Respuesta**: Token Bucket y GCRA son matemáticamente equivalentes como "shapers de tráfico". GCRA (conocido como "leaky bucket algorithm" en ITU-T I.371) se define con dos parámetros: `T` (intervalo mínimo entre celdas) y `τ` (tolerancia a ráfagas). Token Bucket usa `rate` (tokens/segundo) y `capacity` (capacidad máxima de la ráfaga). Son dos representaciones del mismo concepto: limitar la tasa promedio mientras se permiten ráfagas. GCRA es más formal (teoría de colas, estocástica) y Token Bucket es más intuitivo. La equivalencia: `rate = 1/T`, `capacity = τ/T`. La base matemática común es la teoría de tráfico estocástico (Kleinrock, 1975) y los procesos de Poisson.

**Por qué**: El conocimiento de GCRA es valioso porque: (1) Explica por qué Token Bucket es matemáticamente óptimo para rate limiting — no es heurística, tiene fundamento teórico. (2) GCRA puede implementarse con una sola variable de estado (theoretical arrival time) usando aritmética de punto fijo — eficiente en hardware (routers, switches). (3) La biblioteca Bucket4j (Java) usa una implementación de Token Bucket que es funcionalmente GCRA. La conexión entre APIs y telecomunicaciones es profunda: los mismos algoritmos que limitan paquetes en un router limitan requests en una API.

### 6. [Conectar] ¿Cómo se mapean los scopes de OAuth2 a modelos de autorización RBAC (Role-Based Access Control) y ABAC (Attribute-Based Access Control) en APIs? ¿Cuál es más adecuado para TaskFlow?

**Respuesta**: **Scopes → RBAC**: los scopes pueden mapear a roles: scope `read:tasks` y `write:tasks` se agrupan en rol `TASK_USER`. **Scopes → ABAC**: los scopes se combinan con atributos del recurso y del usuario: un usuario con scope `read:tasks` puede leer solo tareas donde `task.ownerId == user.id`. **RBAC** es más simple y adecuado para TaskFlow si las reglas son "admin puede todo, usuario regular solo sus tareas". **ABAC** es necesario si las reglas son complejas: "usuario puede leer tareas de su departamento creadas en los últimos 30 días con prioridad alta". La decisión: RBAC para la mayoría de casos (roles + ownership check). ABAC solo si las reglas de negocio son dinámicas y basadas en atributos contextuales (hora del día, ubicación, nivel de riesgo).

**Por qué**: El NIST SP 800-162 (Guide to ABAC, 2014) define ABAC como "access control based on attributes of the user, resource, and environment." En APIs, ABAC típicamente se implementa con políticas (OPA/Rego, AWS IAM policies, XACML). La mayoría de APIs REST implementan RBAC + ownership (el "user solo puede ver sus recursos" es un attribute check simple) sin llegar a ABAC completo. OAuth2 scopes son coarse-grained (leer tareas, escribir tareas); la autorización fine-grained (cuáles tareas específicas) es responsabilidad del servidor de recursos, no del Auth Server. La clave es no confundir autenticación (quién sos), scopes (qué operaciones podés hacer), con autorización de datos (sobre qué recursos podés hacerlas).

### 7. [Conectar] ¿Cómo interactúa CORS con el almacenamiento de JWT en el frontend? ¿Cuál es la diferencia de seguridad entre guardar el JWT en `localStorage`, `sessionStorage`, o en una cookie `HttpOnly` con `SameSite=Strict`?

**Respuesta**: **(1) localStorage**: accesible via JavaScript (`localStorage.getItem('token')`). Vulnerable a XSS: cualquier script malicioso inyectado puede leer el token. No se envía automáticamente en requests — el frontend debe agregarlo al header `Authorization`. **(2) sessionStorage**: igual que localStorage pero se limpia al cerrar la pestaña. Misma vulnerabilidad XSS. **(3) Cookie HttpOnly + Secure + SameSite=Strict**: el token no es accesible por JavaScript (HttpOnly), solo se envía por HTTPS (Secure), y no se envía en requests cross-site (SameSite). Inmune a XSS pero vulnerable a CSRF si SameSite no es estricto (aunque SameSite=Strict mitiga CSRF). El backend debe leer el JWT de la cookie en lugar del header Authorization.

**Por qué**: OWASP recomienda cookies HttpOnly para sesiones de usuario porque proteger contra XSS es más crítico que la conveniencia de localStorage. Sin embargo, las SPAs modernas con APIs en dominios diferentes (api.taskflow.com vs app.taskflow.com) no pueden usar cookies cross-origin sin SameSite=None + Secure, lo cual reduce la protección CSRF. La práctica más segura para SPAs: **Backend for Frontend (BFF)** — un servidor intermediario (en el mismo dominio que el frontend) maneja las cookies HttpOnly y traduce a Bearer token para la API. Para TaskFlow con frontend separado, si el frontend está en el mismo dominio, cookies HttpOnly. Si está en dominio diferente, localStorage + medidas anti-XSS rigurosas (CSP, sanitización de inputs).

### 8. [Cuestionar] JWT vs opaque tokens para APIs: ¿cuál es realmente más seguro y cuál escala mejor? ¿Debe TaskFlow usar JWT, opaque tokens, o ambos?

**Respuesta**: **JWT**: más escalable (los microservicios validan sin consultar Auth Server — stateless). Menos seguro (no revocable sin blacklist). **Opaque tokens**: más seguro (revocables instantáneamente). Menos escalable (cada validación requiere una llamada al Auth Server o a un cache compartido). La práctica recomendada: **patrón Phantom Token** — el API Gateway recibe un opaque token del cliente, lo intercambia por un JWT interno (consultando al Auth Server), y los microservicios downstream validan el JWT sin llamadas adicionales. El cliente nunca ve el JWT. TaskFlow: si es monolito (como el proyecto del curso), JWT con expiración corta + refresh token opaco es suficiente. Si son microservicios, el patrón Phantom Token via API Gateway (Kong, Apigee, Envoy).

**Por qué**: Curity (empresa de IAM) popularizó el Phantom Token pattern. El tradeoff JWT vs opaque es falso — podés tener ambos. Lo crítico es la capacidad de revocación: si un usuario es despedido o su token es comprometido, debés poder invalidar su acceso en segundos, no en minutos (lo que dure el `exp` del JWT). OWASP recomienda: "Access tokens should have a short lifetime (minutes, not hours). Use refresh tokens with rotation to extend sessions." La rotación de refresh tokens significa que cada vez que usás un refresh token, el viejo se invalida y se emite uno nuevo. Si un refresh token es robado y usado, el token viejo del usuario legítimo se invalida, detectando el robo.

### 9. [Cuestionar] ¿Es `Cache-Control: no-store` en TODAS las respuestas de una API una buena práctica de seguridad o un overkill que desperdicia las ventajas de cacheabilidad de REST?

**Respuesta**: `no-store` en todas las respuestas es overkill que viola la restricción de cacheability de REST sin necesidad. La práctica correcta es granular: **(1) Respuestas con datos sensibles**: `Cache-Control: private, no-store` (perfil del usuario, tokens). **(2) Respuestas públicas inmutables**: `Cache-Control: public, max-age=3600, immutable` (lista de países, catálogo de productos). **(3) Respuestas semi-dinámicas**: `Cache-Control: private, max-age=60` (lista de tareas del usuario — puede cachearse brevemente). **(4) Respuestas que varían por usuario**: `Cache-Control: private` y `Vary: Authorization`. El argumento de seguridad para `no-store` global es válido solo si no confiás en tus clientes HTTP (shared computers, proxies inseguros). Pero para una API consumida por aplicaciones, los clientes son programas que no dejan historial de navegación.

**Por qué**: La restricción de cacheability de REST (Fielding, tesis 2000) es explícita: "The response data must be labeled implicitly or explicitly as cacheable or non-cacheable." La decisión DEBE ser informada, no blanket. El OWASP Testing Guide recomienda revisar headers de caché por endpoint, no aplicar una política global. Si un endpoint devuelve datos no sensibles que cambian poco, cachearlos reduce latencia y carga del servidor — esto es seguridad en profundidad desde otra perspectiva (disponibilidad bajo alta carga). Para TaskFlow: `GET /tasks` (lista del usuario) → `private, max-age=30`. `GET /tasks/{id}` (detalle con datos sensibles) → `private, no-store`. `GET /categories` (referencia inmutable) → `public, max-age=86400`.

### 10. [Cuestionar] ¿HashiCorp Vault vs AWS Secrets Manager vs Doppler para gestión de secretos de API (JWT signing keys, API keys de terceros, DB passwords)? ¿Qué patrón usan los sistemas de producción reales?

**Respuesta**: **(1) HashiCorp Vault**: el estándar de facto en infraestructura multi-cloud y on-premise. Soporta secretos estáticos y dinámicos (genera credenciales de DB temporales), rotación automática, y un modelo de políticas sofisticado. Maduro, open-source, pero operacionalmente complejo (requiere mantener un cluster de Vault). **(2) AWS Secrets Manager / Parameter Store**: integración nativa con AWS, rotación automática para RDS, sin servidor (no gestionás infraestructura). Ideal si estás 100% en AWS. **(3) Doppler**: enfocado en developer experience — sync de secretos entre entornos, integración con CI/CD, interfaz moderna. Más nuevo, menos probado en enterprise. **Patrón real en producción**: Vault para la capa de plataforma (infraestructura); Secrets Manager para servicios AWS; Doppler para equipos de desarrollo que quieren simplicidad. La clave no es cuál herramienta, sino el patrón: NUNCA hardcodear secretos, NUNCA en archivos de configuración commiteados. Siempre inyectar secretos en runtime via environment variables o mounted volumes desde un secret store.

**Por qué**: La pregunta es crucial porque JWT signing keys en texto plano en `application.yml` es una vulnerabilidad crítica. El OWASP Top 10 A07:2021 es "Identification and Authentication Failures" — que incluye mala gestión de secretos. HashiCorp Vault usa Shamir's Secret Sharing para el unseal key. AWS KMS + Secrets Manager integran con IAM para control de acceso. Para TaskFlow en producción: la JWT secret NO debe estar en `application.yml`. Debe cargarse de: variable de entorno (`${JWT_SECRET}` inyectada por el orquestador o CI/CD desde un vault), o Vault Agent sidecar en Kubernetes. Para desarrollo local, usar `application-dev.yml` con secretos de prueba explícitamente marcados (y en `.gitignore`).
