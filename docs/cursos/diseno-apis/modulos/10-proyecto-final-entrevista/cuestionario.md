### 2. [Investigar] ¿Cómo evalúan realmente las empresas FAANG el diseño de APIs en entrevistas técnicas? ¿Qué esperan ver en una pregunta de "Design an API for X" y qué errores eliminan candidatos?

**Respuesta**: En entrevistas FAANG de diseño de sistemas/APIs, evalúan: **(1) Clarificación de requisitos**: ¿preguntaste sobre casos de uso, escala, clientes, restricciones antes de diseñar? **(2) Diseño de contrato**: ¿definiste endpoints, métodos HTTP, códigos de estado, formatos de request/response con ejemplos concretos? **(3) Consideraciones no funcionales**: ¿mencionaste autenticación, rate limiting, paginación, caching, versionado? **(4) Tradeoffs**: ¿discutiste REST vs GraphQL vs gRPC y justificaste tu elección? **(5) Evolución**: ¿cómo evolucionaría esta API sin romper clientes? **Errores que eliminan**: (a) No preguntar requisitos — asumir y diseñar en el vacío. (b) Ignorar seguridad ("asumamos que la autenticación ya está"). (c) No considerar errores — solo diseñar happy path. (d) No mencionar rate limiting, paginación, o caching. (e) Diseñar todo con POST porque "es más simple."

**Por qué**: Gayle Laakmann McDowell ("Cracking the Coding Interview") y Alex Xu ("System Design Interview") documentan que el diseño de APIs es una categoría creciente en entrevistas. Amazon (Bar Raiser process) evalúa específicamente "Customer Obsession" y "Dive Deep" — esperan que preguntes sobre los clientes de la API y explores edge cases. Google evalúa "Design for Scale" y "Tradeoffs". La expectativa no es que diseñes una API perfecta en 45 minutos, sino que demuestres pensamiento estructurado y consideración de todos los aspectos. Para prepararse: practicar diseñando APIs para casos comunes (URL shortener, chat, e-commerce, ride sharing), grabarte, y revisar si cubriste todos los aspectos.

### 3. [Investigar] ¿Cuál es la metodología "12 Factor App" y cómo se aplica específicamente al deployment y operación de APIs REST en producción? ¿Qué factores son más relevantes para APIs?

**Respuesta**: 12 Factor App (Adam Wiggins, Heroku, 2011) es una metodología para construir aplicaciones cloud-native. Factores más relevantes para APIs REST: **(III) Config**: la configuración (URLs de DB, secrets, API keys) debe estar en variables de entorno, no en código. La JWT secret de TaskFlow no debe estar en `application.yml`. **(IV) Backing Services**: DB, cache, SMTP son "attached resources" accedidos via URL. Cambiar de H2 a PostgreSQL debe ser solo cambiar una env var. **(VI) Processes**: stateless — nada de estado en memoria. Perfecto para REST stateless. **(VII) Port Binding**: la app expone HTTP en un puerto. No Tomcat embebido configurado manualmente. **(VIII) Concurrency**: escalar horizontalmente vía procesos, no threads. **(X) Dev/Prod Parity**: desarrollo y producción deben ser lo más similares posible (no "en mi máquina funciona"). **(XI) Logs**: la app escribe logs a stdout; el entorno los captura y routea.

**Por qué**: La metodología original (12factor.net) fue escrita por ingenieros de Heroku basados en su experiencia operando miles de aplicaciones. Aunque data de 2011, sus principios son más relevantes que nunca en la era de Kubernetes y contenedores. Para TaskFlow: el factor III (config en env vars) es crítico — en producción, la DB URL, JWT secret, y credenciales de terceros deben ser inyectadas, no hardcodeadas. El factor VI (stateless) es natural en REST — pero implica que si se necesita estado (rate limiting counters), debe ir a una capa externa (Redis). El factor VIII (concurrency) significa que el rate limiting con `ConcurrentHashMap` (de la clase) funciona en desarrollo pero no en producción con múltiples réplicas — necesitás Redis o similar.

### 4. [Investigar] ¿De dónde surge el movimiento "API-First" y cómo se relaciona con el cambio de paradigma "mobile-first" y "cloud-native"? ¿Qué empresas y autores lo popularizaron?

**Respuesta**: El movimiento API-First tiene raíces múltiples: **(1) Jeff Bezos' memo (2002)**: "toda comunicación entre equipos debe ser a través de APIs" — aunque era interno, sentó precedente. **(2) Twilio (2008) y Stripe (2011)**: demostraron que la API puede ser EL producto, no un complemento. **(3) Mobile-first (2010s)**: cuando las apps mobile necesitaban backends, el diseño API-First surgió naturalmente porque el frontend mobile no podía esperar a que el backend estuviera listo — la API spec era el contrato de desarrollo paralelo. **(4) Microservices (2014)**: cada servicio expone APIs; la API es el contrato entre equipos. Autores: Kin Lane (API Evangelist), Mike Amundsen ("RESTful Web APIs"), Phil Sturgeon ("Build APIs You Won't Hate"), James Higginbotham ("A Practical Approach to API Design"). El término "API-First" fue popularizado por 3scale (ahora Red Hat) y Apigee (ahora Google Cloud) alrededor de 2013-2015.

**Por qué**: La convergencia de mobile + cloud + microservices en la década 2010-2020 creó las condiciones para que API-First pasara de "buena práctica" a "estándar de industria". Kin Lane (apievangelist.com) documentó este cambio durante una década. La ironía: API-First es ahora el estándar recomendado, pero su adopción real es parcial (encuesta Postman 2024: 40% API-First). Muchos equipos aún escriben el código primero y la documentación después. Para TaskFlow, API-First significa: escribir el openapi.yaml completo ANTES del código Java, usarlo como contrato para generar interfaces, y validar que la implementación cumple el contrato.

### 5. [Conectar] Dado el contrato OpenAPI de TaskFlow, ¿cómo se genera automáticamente el código Spring Boot (interfaces o stubs) y qué herramientas permiten mantener el contrato y la implementación sincronizados a lo largo del tiempo?

**Respuesta**: **(1) openapi-generator** (openapi-generator.tech): genera código Spring Boot desde un `openapi.yaml`. Comando: `openapi-generator generate -i openapi.yaml -g spring -o generated/`. Genera interfaces `@Controller` que debés implementar. Modo `delegatePattern: true` genera interfaces delegate que implementás manualmente manteniendo el controlador generado como immutable. **(2) Swagger Codegen**: original de SmartBear (predecesor de openapi-generator), aún usado pero menos mantenido. **(3) contract-driven development con Dredd** (para Node.js) o **Spring Cloud Contract** (para Java) — validan que la implementación cumple la spec. **(4) Para mantener sincronización**: si usás API-First, el código generado se regenera en cada build — si la implementación no cumple el contrato (nuevo parámetro requerido en la spec), el código no compila. Si usás code-first con springdoc, la spec se regenera en runtime pero puede desactualizarse.

**Por qué**: openapi-generator es mantenido por la comunidad (OpenAPI Generator Core Team, 2500+ contributors) y soporta 50+ lenguajes y frameworks. Para Spring Boot, genera DTOs, interfaces de API, y configuración básica. La clave es el `delegatePattern`: en lugar de modificar los controllers generados (que se sobrescribirían en la próxima generación), implementás una interfaz delegate separada. Para CI/CD: agregar la generación al `pom.xml` (plugin `openapi-generator-maven-plugin`) para que cada build verifique que la API implementa el contrato. Si alguien cambia la spec sin actualizar la implementación, el build falla — manteniendo sincronización forzada.

### 6. [Conectar] ¿Cómo se relaciona el mecanismo de entrega de webhooks (reintentos, dead letter queue, firma HMAC) con el patrón Outbox para entrega confiable de eventos en sistemas distribuidos?

**Respuesta**: **Webhooks**: entrega de eventos a sistemas externos sobre HTTP. Problemas: el destino puede estar caído, la red puede fallar, el payload debe ser autenticado. **Outbox Pattern**: en el servicio emisor, los eventos se escriben en una tabla "outbox" en la misma transacción que el cambio de estado. Un proceso separado lee la outbox y publica los eventos (a un message broker o webhook). Relación: para webhooks confiables, se usa Outbox Pattern internamente: cuando una tarea cambia de estado, en la misma transacción se escribe el cambio + un registro en la tabla `webhook_deliveries` (outbox). Un worker separado lee los deliveries pendientes y los intenta entregar al webhook URL con reintentos exponenciales. Si falla después de N reintentos → dead letter queue (tabla `webhook_deliveries` con status=failed para inspección manual).

**Por qué**: El Outbox Pattern fue documentado por Chris Richardson (microservices.io) y es clave para "exactly-once processing" o "at-least-once delivery" en sistemas distribuidos. Sin Outbox, el cambio de estado y el envío del webhook no son atómicos: si el envío falla, el estado cambió pero el webhook no se envió → inconsistencia. Con Outbox, el delivery se registra en la misma transacción → atómico. Luego el worker reintenta hasta éxito o dead letter. El HMAC signature se calcula al momento del envío, usando el `secret` configurado en la suscripción del webhook. La combinación Outbox + reintentos + HMAC es el estándar de facto para webhooks confiables (implementado por Stripe, GitHub, Shopify).

### 7. [Conectar] ¿Cómo se relaciona el patrón BFF (Backend for Frontend) con el API Gateway en una arquitectura de microservicios? ¿Cuándo necesitás ambos y cuándo uno solo es suficiente?

**Respuesta**: **API Gateway**: entrada única para todos los clientes. Maneja cross-cutting concerns: autenticación, rate limiting, logging, routing a servicios downstream. Es genérico — no sabe de las necesidades específicas de cada cliente. **BFF**: un gateway específico por tipo de cliente (mobile BFF, web BFF, third-party BFF). Cada BFF agrega y transforma datos específicamente para las necesidades de ese cliente. Relación: en arquitecturas grandes, el API Gateway es la capa externa (edge) que autentica y protege; los BFFs están detrás del gateway y sirven a clientes específicos. Para TaskFlow pequeño, un API Gateway simple (Spring Cloud Gateway o Kong) alcanza sin BFFs separados. Para TaskFlow con web + mobile + third-party, cada uno tendría su BFF.

**Por qué**: El patrón BFF fue popularizado por Sam Newman (ThoughtWorks, 2015) y es ampliamente usado (Netflix, Spotify, SoundCloud). Newman argumenta que un API Gateway genérico para todos los clientes se convierte en un cuello de botella de coordinación — cada equipo de frontend necesita datos en formas distintas, y negociar cambios en un gateway compartido es lento. Los BFFs son owned por los equipos de frontend, permitiendo que cada uno itere a su velocidad. La diferencia con GraphQL Federation: un BFF es imperativo (código), Federation es declarativa (schema). Para TaskFlow con GraphQL, el gateway federado reemplazaría los BFFs.

### 8. [Cuestionar] Spring Boot vs Quarkus vs Micronaut para APIs REST en 2026: ¿cuál ofrece mejor combinación de performance, developer experience y producción readiness para un proyecto como TaskFlow?

**Respuesta**: **(1) Spring Boot**: el ecosistema más grande, más maduro, más documentación, más talento disponible. Performance buena con Spring Boot 3.x (virtual threads en Java 21), tiempo de startup mejorado con GraalVM native image (aunque aún más lento que Quarkus/Micronaut en native). Ideal para TaskFlow porque el curso ya lo usa y tiene el menor riesgo. **(2) Quarkus**: optimizado para containers/Kubernetes (startup en milisegundos con native image, baja memoria). Excelente developer experience con dev mode (hot reload). Ecosistema más chico que Spring. Ideal si TaskFlow se deploya en serverless/FaaS. **(3) Micronaut**: compile-time DI (sin reflection), startup rápido, baja memoria. Bueno para microservicios y serverless. Ecosistema más chico. **Para TaskFlow**: Spring Boot es la elección correcta por madurez del ecosistema. Si el requisito fuera "serverless cold start < 100ms", Quarkus o Micronaut ganarían.

**Por qué**: Los benchmarks (TechEmpower Web Framework Benchmarks 2024) muestran Quarkus + GraalVM native ~20-30% más rápido que Spring Boot + GraalVM native, y ambos ~5-10x más rápidos que Spring Boot en JVM tradicional. Pero la performance rara vez es el cuello de botella en APIs CRUD — la base de datos lo es. La developer experience de Spring Boot (Spring Initializr, @Autowired, testing con @SpringBootTest) es inigualable en madurez y documentación. El costo de cambiar de framework es más alto que el beneficio de performance para la mayoría de proyectos. La decisión de la clase de usar Spring Boot es acertada.

### 9. [Cuestionar] ¿Es "API-First" sobrevalorado? ¿Cuándo agrega más fricción que valor y cuándo es genuinamente esencial?

**Respuesta**: API-First es sobrevalorado cuando: **(1) La API tiene un solo consumidor** y el contrato se puede negociar en una conversación de 5 minutos. **(2) La API está en prototipo/experimento** y los requisitos cambian diariamente — mantener la spec sincronizada duplica el trabajo. **(3) El equipo es de 1-2 desarrolladores full-stack** que hacen frontend y backend simultáneamente. **(4) La API es interna y efímera** (un servicio que vivirá 3 meses). API-First es genuinamente esencial cuando: **(a) Múltiples equipos/consumidores** dependen de la API y necesitan un contrato estable. **(b) La API es un producto** expuesto a terceros. **(c) El equipo de frontend y backend son distintos** y trabajan en paralelo. **(d) Hay requisitos de compliance** que exigen documentación auditada.

**Por qué**: Phil Sturgeon ("Build APIs You Won't Hate", 2015) reconoce que API-First no es dogma: "API-First is a spectrum. You can adopt the principles without adopting the full toolchain." La clave es pragmatismo: si la API tiene 3 endpoints y 1 consumidor, escribir 500 líneas de OpenAPI YAML es overkill. Si tiene 50 endpoints, 10 consumidores y 3 equipos, no tener OpenAPI es negligencia. Para TaskFlow, el proyecto final del curso es pequeño — API-First es una excelente práctica educativa pero en la vida real dimensionarías la formalidad al contexto.

### 10. [Cuestionar] ¿Cómo evalúan realmente las empresas FAANG el diseño de sistemas en entrevistas de API roles, y cómo difiere del enfoque académico de "aplicar REST puro"? ¿Qué valoran más: pureza arquitectónica o pragmatismo?

**Respuesta**: FAANG valora **pragmatismo informado por principios**, no pureza académica. En una entrevista de diseño de API en Google/Meta/Amazon: **(1) No esperan que menciones HATEOAS** a menos que sea relevante al problema. Esperan que sepas qué es, pero que reconozcas cuándo Nivel 2 es suficiente. **(2) Valoran decisiones justificadas**: "Elegí REST sobre GraphQL porque esta API tiene operaciones CRUD simples y se beneficiará de HTTP caching" es mejor que "REST es el estándar". **(3) Valoran experiencia operativa**: mencionar rate limiting, retry logic, idempotency keys para POST, circuit breaking, monitoring. **(4) Valoran simplicidad**: la API más simple que resuelve el problema, no la más "pura". **(5) Valoran pensamiento de producto**: ¿quién va a usar esta API? ¿cómo se van a equivocar? ¿cómo hacemos que el happy path sea obvio?

**Por qué**: La diferencia con el enfoque académico: la clase enseña "REST puro" como ideal porque es el estándar contra el cual medir. Pero en FAANG, la pureza cede ante la practicidad cuando hay tradeoffs reales. Alex Xu ("System Design Interview Volume 1 & 2") enfatiza que en entrevistas de diseño se evalúa "capacidad de hacer tradeoffs informados", no "recitar teoría". Un candidato que dice "usemos HATEOAS porque es el Nivel 3 de Richardson" sin considerar el costo de implementación del cliente puede fallar. Un candidato que dice "Nivel 2 es suficiente porque los clientes consumirán SDKs generados, no navegarán links dinámicamente" demuestra criterio. La clave es conocer la teoría REST (para saber cuándo estás desviándote) y aplicar pragmatismo (para saber cuándo la desviación es correcta).
