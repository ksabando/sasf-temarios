### 2. [Investigar] ¿Qué es el patrón "Circuit Breaker" popularizado por Michael Nygard en "Release It!" y cómo se aplica al manejo de errores en sistemas distribuidos? ¿Qué estados tiene un circuit breaker y cómo difiere de un simple try-catch?

**Respuesta**: Michael Nygard, en "Release It!" (2007, 2da edición 2018), describió el Circuit Breaker como patrón para manejar fallas en integraciones externas. Tiene tres estados: CLOSED (operación normal, las llamadas pasan), OPEN (el circuito se abre tras N fallas consecutivas, las llamadas se rechazan inmediatamente sin intentar la operación), HALF-OPEN (tras un timeout, se permite UNA llamada de prueba; si falla, vuelve a OPEN; si funciona, vuelve a CLOSED). Diferencia con try-catch: (a) el try-catch intenta SIEMPRE la operación y falla cada vez, el circuit breaker detecta fallas repetidas y deja de intentar protegiendo al sistema externo de sobrecarga, (b) el circuit breaker es stateful a través de múltiples llamadas, el try-catch maneja una llamada individual, (c) el circuit breaker implementa "fail fast" a nivel de infraestructura: si la BD está caída, no malgastás threads esperando timeouts, rechazás inmediatamente y liberás recursos. En Spring, Resilience4j implementa circuit breakers. Clean Code no aborda este patrón porque se enfoca en errores locales, no distribuidos.

**Por qué**: La clase cubre manejo de errores dentro de un solo proceso. En el proyecto final del curso (Spring Boot), los alumnos integrarán servicios externos y necesitarán patrones de resiliencia. Nygard es la referencia fundamental en resiliencia de sistemas y su patrón complementa el manejo de excepciones local con estrategias de sistema.

### 3. [Investigar] ¿Qué son las "Excepciones Chequeadas" en Java y por qué las criticaron Bruce Eckel, Anders Hejlsberg (creador de C#) y otros líderes de la industria? ¿Cómo resolvió C# el problema que Java intentó resolver con checked exceptions?

**Respuesta**: Las excepciones chequeadas (checked) en Java son aquellas que el compilador obliga a declarar en `throws` o capturar con `try-catch`. Fueron una innovación de Java 1.0. Las críticas: (a) Bruce Eckel (autor de "Thinking in Java") escribió en 2003 "Does Java Need Checked Exceptions?" argumentando que incentivan malas prácticas: los desarrolladores tragan excepciones con `catch (Exception e) {}` o las envuelven en RuntimeException para evitar declararlas, anulando su propósito; (b) Anders Hejlsberg (C# architect) decidió NO incluir checked exceptions en C# argumentando que la verificabilidad de tipos en excepciones no escala: en un sistema grande, el throws clause de un método se vuelve extremadamente largo o las excepciones se generalizan a `throws Exception`, eliminando el valor; (c) las lambdas de Java 8 no pueden lanzar checked exceptions, forzando workarounds. C# resolvió el problema con: documentación XML de excepciones (opcional, no forzada por compilador) + análisis estático opcional. La comunidad Java ha migrado a unchecked exceptions en la práctica (Spring, Hibernate).

**Por qué**: La clase menciona que Clean Code "prefiere unchecked exceptions" citando a Robert C. Martin, pero sin explorar el debate histórico que llevó a esta conclusión. Eckel y Hejlsberg hicieron contribuciones fundamentales al diseño de lenguajes. El alumno debe entender que las checked exceptions no son "malas" per se —son un experimento de diseño de lenguaje que la industria evaluó y mayoritariamente rechazó.

### 4. [Investigar] ¿Qué es "Structured Logging" y cómo se diferencia de simplemente "poner contexto en el mensaje de la excepción"? ¿Qué proponen herramientas como SLF4J con Markers y Mapped Diagnostic Context (MDC) para el manejo de errores en producción?

**Respuesta**: Structured Logging (logging estructurado) es la práctica de loggear eventos como pares clave-valor en formato JSON/estructurado en lugar de strings planos. Un mensaje de excepción tradicional: `"Payment failed for customer 12345: balance 50.00 < 75.00"`. Versión estructurada: `{"event": "payment_failed", "customerId": "12345", "balance": 50.00, "required": 75.00, "errorCode": "INSUFFICIENT_FUNDS"}`. La diferencia: (a) los sistemas de agregación de logs (ELK, Splunk, Datadog) pueden indexar, buscar y graficar campos estructurados; no pueden hacer queries eficientes sobre strings planos, (b) MDC (Mapped Diagnostic Context) de SLF4J permite inyectar contexto automáticamente en TODOS los logs de un request (requestId, userId, tenant) sin que cada excepción los incluya manualmente, (c) los Markers de SLF4J permiten categorizar eventos (BUSINESS_ERROR, TECHNICAL_ERROR, SECURITY) para filtrar y enrutar logs. La clase dice "provee contexto en excepciones" pero no enseña que en sistemas modernos, el contexto debe ser ESTRUCTURADO para ser procesable por máquinas, no solo legible por humanos.

**Por qué**: La clase se enfoca en el mensaje de excepción legible por humanos. En producción, los logs son consumidos por sistemas automáticos. Structured logging es un estándar de facto (todas las plataformas cloud lo recomiendan) y el alumno debe saber que "poner contexto" en 2026 significa proveer datos estructurados, no solo strings descriptivos.

### 5. [Conectar] La clase menciona `Optional<T>` y el Null Object Pattern como alternativas a null. ¿Cómo maneja Rust el problema de "ausencia de valor" sin null y sin Optional? ¿Qué es `Option<T>` en Rust y cómo se diferencia del `Optional<T>` de Java en términos de seguridad y ergonomía?

**Respuesta**: Rust elimina `null` del lenguaje por completo. Usa `Option<T>` (enum con dos variantes: `Some(T)` y `None`), pero a diferencia de `Optional<T>` de Java: (a) `Option<T>` en Rust no es nullable —un `Option<T>` NUNCA es null, a diferencia de `Optional` de Java que PUEDE ser null (ej. `Optional.of(null)` lanza NPE, pero `Optional.ofNullable(null)` retorna `Optional.empty()` —y alguien puede pasar `null` donde se espera `Optional`), (b) Rust tiene pattern matching exhaustivo: el compilador OBLIGA a cubrir ambos casos `Some` y `None` en cada `match`; en Java podés llamar a `.get()` sin verificar y obtenés `NoSuchElementException`, (c) Rust provee el operador `?` para propagación temprana de `None` (similar al `?.` de Kotlin pero a nivel de función y tipado), (d) `Option` en Rust tiene zero-cost abstraction (el compilador optimiza `Option<&T>` a un puntero nullable a nivel máquina, sin overhead). La diferencia fundamental: en Java, `Optional` es una herramienta de biblioteca que convive con null; en Rust, `Option` es parte del sistema de tipos y null NO EXISTE como concepto del lenguaje.

**Por qué**: La clase presenta Optional como la solución, pero no discute sus limitaciones en Java (Optional mismo puede ser null, no es serializable para JPA, no se puede usar como parámetro de método según Brian Goetz). Rust muestra cómo un lenguaje diseñado desde cero resuelve el problema de raíz. El contraste ayuda al alumno a entender que Clean Code hace lo mejor posible con las herramientas de Java, pero el problema de null es una limitación del lenguaje.

### 6. [Conectar] La clase habla de "fail fast" con `Objects.requireNonNull`. ¿Cómo se relaciona el fail fast con el concepto de "Design by Contract" de Bertrand Meyer? ¿Qué ofrecen herramientas como `@NonNull` de Checker Framework más allá de `Objects.requireNonNull`?

**Respuesta**: Bertrand Meyer introdujo "Design by Contract" (DbC) en el lenguaje Eiffel (1986, "Object-Oriented Software Construction"). DbC define tres tipos de aserciones: precondiciones (lo que el caller debe garantizar), postcondiciones (lo que el método garantiza al retornar), invariantes (lo que la clase garantiza siempre). `Objects.requireNonNull` es una precondición escrita manualmente. El Checker Framework (desarrollado por Michael Ernst y su equipo en University of Washington, integrable en Java) va más allá: con la anotación `@NonNull`, el compilador verifica en TIEMPO DE COMPILACIÓN que ningún valor potencialmente null llegue a un parámetro anotado como `@NonNull` —a través de TODA la cadena de llamadas del programa. La diferencia: (a) `requireNonNull` es tiempo de ejecución (fail fast en runtime), (b) `@NonNull` de Checker Framework es tiempo de compilación (fail fast antes de ejecutar), (c) DbC con Eiffel chequea precondiciones automáticamente en testing/desarrollo. La evolución: fail fast comenzó en runtime, la industria avanza hacia fail fast en compilación.

**Por qué**: La clase recomienda fail fast pero no explora el "Design by Contract" que es la teoría fundacional detrás de la validación de entrada. Meyer es una figura central en ingeniería de software y el Checker Framework demuestra que las limitaciones de null en Java pueden mitigarse con tooling avanzado sin cambiar de lenguaje. Esto complementa el módulo con herramientas modernas.

### 7. [Conectar] La clase menciona `@RestControllerAdvice` para manejo global de excepciones en Spring. ¿Qué es "Problem Details" (RFC 9457, antes RFC 7807) y cómo Spring lo implementa? ¿Por qué es superior a usar un `ErrorResponse` personalizado como sugiere la clase?

**Respuesta**: RFC 9457 (antes RFC 7807, "Problem Details for HTTP APIs", 2016) define un formato estándar para respuestas de error HTTP: `{"type": "https://api.example.com/errors/insufficient-funds", "title": "Insufficient Funds", "status": 400, "detail": "Account 12345 has balance 50.00 but required 75.00", "instance": "/payments/789"}`. Spring implementa esto con `ProblemDetail` (desde Spring Framework 6 / Boot 3) y `ErrorResponse`. Es superior a un `ErrorResponse` personalizado porque: (a) es un ESTÁNDAR —cualquier cliente HTTP que consuma tu API (Postman, curl, otros microservicios) puede parsear el error sin documentación personalizada, (b) los campos `type` (URI que identifica el tipo de error), `instance` (URI del recurso que causó el error), y `title` son semánticamente precisos y permiten automatización, (c) herramientas de monitoreo y API Gateways pueden procesar Problem Details automáticamente. La clase propone crear `ErrorResponse` propio, lo cual es comprensible pre-2016, pero hoy usar el estándar es más interoperable.

**Por qué**: La clase usa un formato de error ad-hoc. La RFC 9457 es el estándar moderno y Spring lo soporta nativamente. El alumno debe conocer que para APIs HTTP, existen estándares que reemplazan soluciones caseras.

### 8. [Cuestionar] La clase recomienda "nunca retornar null". Pero Java mismo retorna null en muchas APIs estándar (`Map.get(key)`, `List.get(index)`, `System.getProperty()`). ¿Es realista "nunca retornar null" cuando el ecosistema estándar no lo cumple? ¿Qué estrategia de "boundary" proponen autores como Michael Feathers para lidiar con APIs que retornan null?

**Respuesta**: "Nunca retornar null" es un ideal de diseño para TU código, no una regla para wrappers de APIs externas. Las APIs del JDK que retornan null preceden a `Optional` (introducido en Java 8, 2014). Michael Feathers sugiere en "Working Effectively with Legacy Code" la estrategia de "seam": creá una DELGADA capa de adaptación (seam) alrededor de las APIs externas que retornan null, y en TU código de dominio nunca retornes null. Ejemplo: en lugar de propagar `Map.get(key)` que puede retornar null, creás un método `getRequired(key)` que lanza excepción o retorna `Optional`. La capa de adaptación es ESTRECHA (pocas líneas, cerca del boundary) y contamina mínimamente. El realismo: tu código de negocio usa `Optional` y nunca ve null; tu capa de adaptación maneja los nulls del JDK/librerías en los bordes. La regla es "minimizá la superficie donde null puede aparecer". El alumno debe entender que Clean Code describe un IDEAL, y la ingeniería consiste en gestionar la distancia entre el ideal y la realidad con patrones de contención.

**Por qué**: La clase da una regla absoluta que ningún proyecto Java real puede cumplir sin wrappers. Feathers provee la estrategia de contención que transforma la regla en práctica. El alumno debe saber que "nunca retornar null" significa "nunca retornar null en tu API de dominio", no "reescribí el JDK".

### 9. [Cuestionar] La clase prefiere unchecked exceptions argumentando que las checked violan el Open/Closed Principle. ¿Qué argumentos de defensa de las checked exceptions sostienen que en APIs críticas (ej. sistemas de vuelo, dispositivos médicos), la verificabilidad forzada por el compilador es EXACTAMENTE lo que se necesita? ¿Hay dominios donde checked exceptions son apropiadas?

**Respuesta**: En sistemas de alta criticidad (aviónica DO-178C, dispositivos médicos IEC 62304, sistemas financieros con requisitos regulatorios), la verificabilidad en tiempo de compilación es un REQUISITO, no una preferencia. En estos dominios, las checked exceptions forzan al programador a considerar cada modo de falla: no podés OLVIDARTE de manejar un `IOException` porque el compilador no te deja compilar. Esto se alinea con la filosofía de "correctness by construction". James Gosling defendió las checked exceptions exactamente con este argumento: en sistemas donde un error no manejado puede causar pérdida de vidas o millones de dólares, el compilador debe ser un aliado que imponga disciplina. El problema no son las checked exceptions en SÍ, sino que Java las APLICÓ INDISCRIMINADAMENTE a todas las APIs —incluyendo `SQLException` en un CRUD simple. En dominios críticos, checked exceptions + herramientas de análisis estático (que verifican que cada modo de falla tiene un handler documentado) es la combinación correcta. Clean Code asume desarrollo de software empresarial, no sistemas críticos.

**Por qué**: La clase generaliza desde software empresarial. El alumno debe entender que las reglas de Clean Code tienen contexto y que en dominios regulados, "checked exceptions violan OCP" cede ante "el compilador debe garantizar que ningún error pase desapercibido". Conocer los límites de aplicabilidad de los principios es señal de seniority.

### 10. [Cuestionar] La clase dice que `catch (Exception e) { e.printStackTrace(); }` es mala práctica. ¿Qué dice la comunidad sobre el logging de excepciones a nivel de framework? ¿Existe el riesgo de "double logging" (loggear la misma excepción en múltiples capas) y cómo lo resuelve la práctica de "log or rethrow, never both"?

**Respuesta**: La práctica "log or rethrow, never both" (loggeá o relanzá, nunca ambos) es un estándar de la comunidad Java (documentado en las guías de estilo de Google, en Effective Java de Joshua Bloch, Item 63 y 75). El problema: si el servicio loggea la excepción Y la relanza, y el controller advice también la loggea, la misma excepción aparece 2+ veces en los logs, creando confusión en la correlación de eventos y llenando el storage de logs. La regla: cada excepción debe ser loggeada UNA SOLA VEZ, en el nivel MÁS EXTERNO que tiene contexto suficiente. En una arquitectura Spring típica: el servicio lanza la excepción con contexto rico; el `@RestControllerAdvice` la captura, loggea UNA vez con el requestId del MDC, y retorna la respuesta HTTP. Las capas intermedias NUNCA loggean y relanzan —solo agregan contexto con "exception chaining" (pasan la causa original). La clase solo dice "no uses printStackTrace" pero no enseña la estrategia de logging en capas, que es donde los equipos reales sufren.

**Por qué**: La clase critica `printStackTrace` sin proveer la alternativa arquitectónica. "Log or rethrow" es el complemento necesario para que la recomendación de la clase sea accionable. Bloch (Effective Java) es lectura obligatoria para cualquier desarrollador Java y provee la justificación detallada de esta práctica.
