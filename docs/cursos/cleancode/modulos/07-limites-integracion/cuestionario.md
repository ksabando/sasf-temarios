### 2. [Investigar] ¿Qué es el "Strangler Fig Pattern" de Martin Fowler y cómo se aplica a la modernización gradual de un sistema legacy? ¿Qué relación tiene con los límites y adapters?

**Respuesta**: Martin Fowler describió el Strangler Fig Pattern en 2004 (martinfowler.com, inspirado en la higuera estranguladora que crece alrededor de un árbol huésped hasta reemplazarlo). La estrategia: en lugar de reescribir un sistema legacy de golpe (big-bang rewrite, extremadamente riesgoso), construís un NUEVO sistema alrededor del legacy, y gradualmente redirigís funcionalidad del viejo al nuevo mediante un "routing layer" que intercepta las requests y decide qué sistema las maneja. Los adapters son la herramienta CLAVE: el nuevo sistema expone los MISMOS puertos/interfaces que el viejo, por lo que el routing layer es transparente para los clientes. El sistema legacy eventualmente queda reducido a cero funcionalidad y se retira. Relación con el módulo: los adapters no solo sirven para aislar librerías de terceros —son la herramienta fundamental para modernizar sistemas legacy de manera incremental. El proyecto final del curso (refactorizar un sistema legacy de biblioteca) es EXACTAMENTE un escenario donde el Strangler Fig se aplicaría si el sistema estuviera en producción.

**Por qué**: La clase enfoca los límites como integración con código externo (librerías). Fowler extiende el concepto al límite más peligroso: tu propio código legacy. El Strangler Fig es el patrón más importante que el alumno debe conocer para trabajar con sistemas legacy en producción.

### 3. [Investigar] ¿Qué son los "Consumer-Driven Contracts" (CDC) y cómo herramientas como Pact o Spring Cloud Contract implementan este concepto? ¿Por qué es una evolución del enfoque de Learning Tests que la clase propone?

**Respuesta**: Consumer-Driven Contracts (Ian Robinson, 2006, ThoughtWorks) invierte el modelo tradicional de API: en lugar de que el PROVEEDOR defina el contrato y los CONSUMIDORES se adapten, cada consumidor publica sus EXPECTATIVAS del provider como un contrato (ej. "cuando llamo a GET /users/5, espero JSON con campos id, name, email"). El provider recopila todos los contratos de todos sus consumidores y verifica que su implementación los SATISFACE. Herramientas: Pact (consumer escribe tests que generan contratos; provider verifica contra esos contratos en CI); Spring Cloud Contract (provider define contratos con stubs generados automáticamente para consumers). Relación con Learning Tests: ambos verifican que una dependencia externa se comporta como esperamos. La diferencia: (a) Learning Tests son UNILATERALES (vos testeás que entendiste la API), (b) CDC es BILATERAL (el provider se compromete a no romper los contratos de sus consumers), (c) CDC escala a múltiples equipos y servicios, Learning Tests son para una librería que no se comunica con vos.

**Por qué**: La clase propone Learning Tests para librerías. CDC extiende la filosofía de verificar expectativas a integraciones entre servicios, que es el caso más común en arquitecturas de microservicios que el alumno encontrará profesionalmente.

### 4. [Investigar] ¿Qué clasificación de "Test Doubles" estableció Gerard Meszaros en "xUnit Test Patterns"? ¿Qué tipos de doubles son más apropiados para testear límites y adapters, y por qué?

**Respuesta**: Gerard Meszaros, en "xUnit Test Patterns: Refactoring Test Code" (2007), clasificó los test doubles en 5 tipos: (1) Dummy: objeto que se pasa pero nunca se usa, solo para satisfacer parámetros. (2) Stub: retorna respuestas predefinidas siempre igual. (3) Spy: registra las llamadas que recibe para verificarlas después. (4) Mock: objeto preprogramado con expectativas de cómo DEBE ser llamado (verifica comportamiento). (5) Fake: implementación ligera pero funcional (ej. base de datos en memoria, no mock de DB). Para testear adapters: (a) Fake del servicio externo es IDEAL —simula comportamiento real (happy path, timeouts, errores), (b) Mock solo cuando el comportamiento exacto del adapter hacia el exterior es la expectativa, (c) Stub para depender del dato que el adapter retorna sin importar cómo. La clase menciona "mocks" informalmente pero sin la taxonomía de Meszaros, lo cual lleva a usar mock para todo y producir tests frágiles acoplados a implementación.

**Por qué**: Meszaros es LA referencia en patrones de testing. Sin su taxonomía, los desarrolladores tienden a abusar de mocks (testeando implementación en lugar de comportamiento) o no saber cuándo un Fake es mejor. Esto es esencial para el módulo porque los adapters EXISTEN para ser testeados con doubles apropiados.

### 5. [Conectar] La clase describe "Learning Tests" para explorar APIs de terceros. ¿Cómo se relaciona este concepto con los "Characterization Tests" de Michael Feathers y qué diferencia fundamental hay entre ambos? ¿Cuándo usarías uno y cuándo el otro?

**Respuesta**: Ambos son tests que no prueban corrección sino que DOCUMENTAN comportamiento existente. La diferencia fundamental es el OBJETO de estudio: (a) Learning Tests: exploran una API EXTERNA NUEVA que vas a integrar —el comportamiento documentado debería ser ESTABLE (la librería publica su API). (b) Characterization Tests (Feathers, "Working Effectively with Legacy Code", 2004): documentan el comportamiento de tu PROPIO CÓDIGO LEGACY que NO entendés completamente y que NO TIENE TESTS —el comportamiento documentado puede ser INCORRECTO (bugs), pero lo documentás ANTES de refactorizar para detectar regresiones. Feathers es explícito: estos tests no validan que el código sea correcto, solo que "así funcionaba antes de que yo lo tocara". Cuándo usar: Learning Tests cuando integrás algo nuevo de afuera. Characterization Tests cuando vas a modificar código legacy propio sin tests. Ambos comparten la filosofía: "primero entiendo qué hace, luego cambio".

**Por qué**: La clase presenta Learning Tests para APIs externas. El proyecto del curso involucra refactorizar un sistema legacy (de biblioteca), donde los Characterization Tests son la herramienta PRINCIPAL. Sin ellos, refactorizar código legacy es cirugía sin anestesia. Feathers es el complemento indispensable al capítulo de Límites cuando el "tercero" es tu yo del pasado.

### 6. [Conectar] La clase recomienda encapsular código de terceros detrás de interfaces (adapter). ¿Cómo extiende el "Dependency Inversion Principle" (la D de SOLID) este concepto? ¿Qué dice Robert C. Martin sobre la diferencia entre "depender de interfaces" y "depender de abstracciones"?

**Respuesta**: El Dependency Inversion Principle (Martin, 1996, artículo en C++ Report) establece: (a) módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de abstracciones. (b) Las abstracciones no deben depender de detalles; los detalles deben depender de abstracciones. La clase muestra cómo encapsular código de terceros (detalle) detrás de una interfaz (abstracción), pero Martin va más allá: la interfaz debe ser PROPIEDAD del módulo de alto nivel (tu dominio), no del módulo de bajo nivel. Esto es sutil pero crucial: `PaymentGateway` (interfaz) vive en el paquete de dominio `com.empresa.pagos`, NO en `com.terceros.fastpay`. La clase no enfatiza la PROPIEDAD de la interfaz, que es la verdadera inversión de dependencia. Si la interfaz `PaymentGateway` está en el paquete del adapter, no hay inversión real —el dominio sigue dependiendo de un paquete que depende del tercero. La regla completa: (1) creá la interfaz en tu dominio, (2) el adapter IMPLEMENTA tu interfaz, (3) el adapter depende del tercero, (4) tu dominio NO depende de nada externo.

**Por qué**: La clase presenta el adapter como encapsulamiento sin enfatizar que la DIRECCIÓN de la dependencia es la clave. Sin esta precisión, los alumnos crean adapters donde la interfaz está junto al adapter (mismo paquete) y el dominio depende de ese paquete —sin inversión real. DIP es el principio arquitectónico más malinterpretado y su aplicación correcta es lo que distingue diseño limpio de adapters cosméticos.

### 7. [Conectar] La clase explica que los Learning Tests "alertan cuando una librería cambia". ¿Cómo se relaciona esto con el versionado semántico (SemVer) y qué limitaciones tiene confiar SOLO en Learning Tests sin verificar el semantic versioning de dependencias?

**Respuesta**: Semantic Versioning (Tom Preston-Werner, semver.org, 2011) establece MAJOR.MINOR.PATCH: MAJOR para breaking changes, MINOR para features nuevas compatibles, PATCH para bug fixes. La conexión con Learning Tests: si una librería cambia MINOR o PATCH, tus Learning Tests NO deberían fallar (si fallan, el autor de la librería violó SemVer). Si cambia MAJOR, tus tests DEBERÍAN fallar en algún punto. Las limitaciones de depender solo de Learning Tests: (a) si tenés 100 dependencias, ejecutar Learning Tests para TODAS en cada upgrade es costoso —el versionado semántico te permite priorizar: upgrades PATCH no deberían romper nada y podés automatizarlos (Renovate, Dependabot), (b) Learning Tests no cubren TODOS los comportamientos de una librería —solo los que vos usás. Un breaking change en una API que no usás pasará desapercibido en tus tests pero puede ser señal de que la librería es inestable, (c) herramientas como `dependabot` + CI que ejecutan tu suite completa de tests en upgrades automáticos combinan SemVer + verificación de comportamiento. La clase presenta Learning Tests como solución aislada; en la práctica, es una capa de una estrategia multi-capas de gestión de dependencias.

**Por qué**: La clase no menciona versionado de dependencias. En el desarrollo real, gestionar versiones es tan importante como aislar dependencias. El alumno debe entender que los Learning Tests son parte de un ecosistema de prácticas (SemVer, lockfiles, automated dependency updates, reproducible builds).

### 8. [Cuestionar] La clase presenta los adapters como la solución para desacoplar código de terceros. ¿Qué sostiene Yegor Bugayenko sobre el uso excesivo de interfaces y adapters? ¿Cuál es su crítica a lo que él llama "interface-itis" y cómo se relaciona con el principio YAGNI?

**Respuesta**: Yegor Bugayenko, en "Elegant Objects" (2017, Volumen 2), critica lo que llama "interface-itis": la práctica de crear interfaces para todo "por si acaso cambia la implementación". Su argumento: (a) las interfaces no son gratis —cada interfaz es una capa de indirección que hace el código más difícil de navegar, (b) "interfaz + única implementación" viola YAGNI: si solo tenés un `PayPalAdapter`, ¿para qué existe `PaymentGateway`? La respuesta "para testear" no alcanza —podés mockear la clase concreta o usar un Fake, (c) la proliferación de interfaces oscurece el "entry point" real: cuando tenés 50 interfaces y 50 implementaciones, encontrar QUÉ implementación se usa en producción requiere navegar la configuración de inyección de dependencias. Bugayenko aboga por: crear interfaz SOLO cuando hay al menos DOS implementaciones en producción (no en tests). La interface prematura es una abstracción especulativa. La clase recomienda adapters como principio; Bugayenko recuerda que cada adapter es costo de complejidad.

**Por qué**: La clase asume que los adapters son siempre buenos. Bugayenko es una voz crítica que obliga a justificar cada adapter. El alumno debe poder argumentar CUÁNDO un adapter se justifica y cuándo es sobre-ingeniería, en lugar de aplicar el patrón por inercia.

### 9. [Cuestionar] La clase recomienda aislar el código de terceros en adapters. ¿Qué sucede con librerías que se vuelven "estándar de la industria" y se integran profundamente en todo el código (ej. Jackson para JSON en Java, React para UI)? ¿Es práctico envolver Jackson en un adapter? ¿Dónde trazás la línea entre "dependencia aceptable" y "dependencia que requiere adapter"?

**Respuesta**: La línea se traza con el criterio de "riesgo de cambio" y "profundidad de integración". (a) Jackson es ubicuo en Java: está en Spring Boot, en cada serialización, y wrappearlo sería un adapter colosal que duplicaría todo su API. Riesgo de cambio: BAJO (es el estándar de facto, mantenido por FasterXML, cambios breaking son raros). Conclusión: no necesita adapter. (b) React en frontend es ubicuo y profundo: no tiene sentido wrappearlo. (c) Una pasarela de pago específica (MercadoPago, Stripe) tiene riesgo de cambio ALTO (cambian APIs, cambian precios, pueden ser reemplazadas por un competidor), profundidad de integración BAJA (llamás 3-4 endpoints). Conclusión: necesita adapter. (d) Una librería de logging: profundidad ALTA (está en todas partes), riesgo de cambio BAJO. Conclusión: usar SLF4J como fachada (que ya es un adapter estándar), no crear tu propio wrapper. La regla práctica: creá adapter cuando la dependencia es REEMPLAZABLE y su API no es ubicua. No creés adapter para el framework o las librerías que definen el paradigma de tu stack.

**Por qué**: La clase da una regla (siempre encapsular) sin criterio de costo/beneficio. El resultado es que alumnos crean wrappers para todo, incluyendo `List` o `Optional`, y terminan con sistemas llenos de indirección. El equipo de Google tiene guías sobre "acceptable dependencies": librerías que todo el código puede usar directamente (Guava, protobuf) vs. librerías que requieren wrapper. El alumno debe desarrollar criterio pragmático.

### 10. [Cuestionar] La clase propone caracterizar código legacy con tests. En la práctica, caracterizar una clase de 2000 líneas sin tests previos puede tomar días. ¿Qué técnica de "seam" propone Michael Feathers para testear código legacy sin caracterizarlo completamente? ¿Qué es un "sensing variable" y cómo se usa para refactoring seguro sin cobertura total?

**Respuesta**: Michael Feathers define "seam" como un punto en el código donde podés cambiar el comportamiento sin editar directamente ese punto. Técnicas específicas para testear sin caracterizar TODO: (a) "Extract and Override Call": en lugar de testear la clase entera, en la subclase de test sobreescribís la dependencia problemática (ej. `getConnection()` que requiere BD real) para retornar un fake. No testeás la clase original —reemplazás UNA dependencia para aislar el comportamiento que querés modificar. (b) "Sensing Variable": una variable temporal que agregás al código para "espiar" el estado interno en tests. Feathers sugiere que durante la refactorización, agregar variables de sensing que capturen efectos intermedios y luego removerlas cuando el código esté limpio y testeable. La filosofía: no necesitás 80% de cobertura ANTES de refactorizar; necesitás seams estratégicos que te permitan cambiar partes con confianza. La clase asume que caracterizarás todo el legacy previamente; Feathers —que lidió con código mucho peor— propone técnicas para cambiar código mientras lo testeás incrementalmente.

**Por qué**: El proyecto final pide >80% de cobertura y la clase sugiere characterization tests. En código legacy real, llegar a 80% de cobertura antes de refactorizar es inviable. Feathers es el complemento pragmático que enseña a refactorizar con red de seguridad PARCIAL, que es la realidad de todo proyecto legacy. El alumno debe conocer estas técnicas para no paralizarse ante la magnitud del código a testear.
