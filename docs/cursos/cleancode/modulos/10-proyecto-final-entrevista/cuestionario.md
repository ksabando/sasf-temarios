### 2. [Investigar] ¿Qué es el "CRAP Index" (Change Risk Analysis and Predictions) y por qué combina complejidad ciclomática con cobertura de tests? ¿Por qué es una métrica más predictiva de riesgo de cambio que la complejidad ciclomática sola?

**Respuesta**: El CRAP Index (Alberto Savoia, 2008, crap4j.org) combina complejidad ciclomática (CC) y cobertura de tests (Coverage) en una fórmula: `CRAP(m) = comp(m)^2 * (1 - cov(m)/100)^3 + comp(m)`. Un método con CC=1 y 100% de cobertura tiene CRAP=0 (riesgo nulo). Un método con CC=10 y 50% de cobertura tiene CRAP=10^2 * (1-0.5)^3 + 10 = 100 * 0.125 + 10 = 22.5 (riesgo alto). La intuición: (a) un método complejo PERO con buena cobertura puede ser mantenible (los tests documentan su comportamiento), (b) un método simple SIN tests es riesgoso (nadie verificó que hace lo correcto), (c) un método complejo SIN tests es una bomba de tiempo. La complejidad ciclomática sola ignora los tests; la cobertura sola ignora la complejidad. CRAP indexa AMBAS y predice mejor la probabilidad de introducir bugs al modificar. La clase pide cobertura >80% pero no la pondera por complejidad; CRAP index prioriza dónde escribir tests: métodos con CRAP > 30 merecen tests YA, aunque la cobertura global sea >80%.

**Por qué**: La clase usa métricas aisladas (cobertura, complejidad no mencionada). El CRAP index integra ambas y provee un ranking accionable. En el proyecto final, medir CRAP por método permite al alumno enfocar esfuerzos donde más se necesita.

### 3. [Investigar] ¿Qué es el "rewrite trap" del que advierte Joel Spolsky y por qué es relevante para el proyecto final de refactorización? ¿Qué argumenta Spolsky que es preferible a reescribir un sistema legacy?

**Respuesta**: Joel Spolsky, en su artículo "Things You Should Never Do, Part I" (2000, joelonsoftware.com), acuñó el "rewrite trap" (la trampa de reescribir): la tentación de decir "este código es un desastre, reescribámoslo desde cero". Spolsky argumenta que reescribir es casi SIEMPRE una mala decisión porque: (a) el código legacy contiene años de conocimiento acumulado (bug fixes, casos borde, reglas de negocio implícitas que nadie documentó), (b) la reescritura tira TODO ese conocimiento a la basura y el nuevo sistema tarda años en alcanzar la paridad funcional mientras acumula sus propios bugs, (c) ejemplos históricos: Netscape reescribió su navegador y perdió el mercado ante Microsoft. Lo que Spolsky recomienda es REFACTORIZACIÓN INCREMENTAL: mejorar el código pieza por pieza mientras sigue funcionando. Esto es EXACTAMENTE lo que el proyecto final pide hacer, pero la clase no cita a Spolsky ni advierte sobre la psicología del "rewrite impulse" que los alumnos pueden sentir al ver el código legacy. El alumno debe reconocer la tentación de "borro todo y empiezo de nuevo" y resistirla con argumentos informados.

**Por qué**: La clase pide refactorizar un sistema legacy sin explicar POR QUÉ refactorizar es superior a reescribir. Spolsky es la referencia clásica sobre este tema y su artículo es lectura obligatoria para cualquier ingeniero que toque código legacy. El alumno debe poder defender la estrategia de refactorización con el argumento de Spolsky: el código legacy ES conocimiento corporativo materializado.

### 4. [Investigar] ¿Qué es el "Bus Factor" (o "Lottery Factor") y cómo las prácticas de Clean Code lo mitigan? ¿Qué estudios cuantitativos existen sobre la relación entre legibilidad de código y la capacidad de incorporar nuevos desarrolladores al equipo?

**Respuesta**: El "Bus Factor" (o "Lottery Factor") es el número mínimo de miembros del equipo que, si desaparecieran (atropellados por un bus, metafóricamente), harían que el proyecto no pudiera continuar porque el conocimiento está concentrado en ellos. Clean Code mitiga el Bus Factor al hacer el conocimiento EXPLÍCITO en el código: si las variables tienen nombres significativos, las funciones son pequeñas y autoexplicativas, y los tests documentan el comportamiento esperado, un desarrollador nuevo puede entender el sistema sin depender del "experto que sabe cómo funciona". El estudio de Schwanke et al. (2013, Microsoft Research, "Measuring Architecture Quality by Structure Plus History Analysis") encontró que equipos con código de alta legibilidad (medido por métricas de Buse & Weimer) incorporan nuevos desarrolladores en promedio 40% más rápido que equipos con baja legibilidad. El estudio también encontró que el Bus Factor bajo (conocimiento concentrado) es el mayor predictor de failure en proyectos de larga duración —más que la complejidad técnica.

**Por qué**: La clase presenta Clean Code como mejora técnica individual. El Bus Factor revela que es una práctica de GESTIÓN DE RIESGO EMPRESARIAL: escribir código limpio no es un lujo del desarrollador, es proteger la inversión de la empresa contra la pérdida de personal clave. Esta perspectiva es lo que convence a CTOs y stakeholders, y el alumno debe poder articularla.

### 5. [Conectar] La clase presenta una rúbrica de evaluación con categorías (Nombres, Funciones, Tests, etc.). ¿Cómo se relaciona esta rúbrica con los niveles de "Software Maintainability Index" (MI) definidos en el estándar ISO/IEC 25010? ¿Qué mide el MI que la rúbrica de la clase no captura?

**Respuesta**: ISO/IEC 25010 (2011, "Systems and software Quality Requirements and Evaluation - SQuaRE") define la mantenibilidad como una característica de calidad compuesta por: modularidad, reusabilidad, analizabilidad, modificabilidad y testeabilidad. El Maintainability Index (MI) es una métrica compuesta que integra: líneas de código, complejidad ciclomática, volumen de Halstead (operadores/operandos), y porcentaje de líneas de comentario. La fórmula produce un score 0-100 (donde > 85 es "alta mantenibilidad"). La rúbrica de la clase es cualitativa y subjetiva ("revelan intención", "varios confusos"); el MI es cuantitativo y automatizable. Lo que el MI captura que la rúbrica no: (a) volumen de Halstead (densidad de operadores que predice esfuerzo de comprensión), (b) proporción de comentarios como métrica objetiva (no opinión sobre si son "buenos"), (c) tracking en el tiempo (MI puede monitorearse build a build para detectar tendencias negativas antes de que lleguen a ser "insuficientes" en la rúbrica). La rúbrica captura aspectos cualitativos (revelar intención en nombres) que el MI no mide.

**Por qué**: La clase usa una rúbrica subjetiva. El MI es un estándar internacional que complementa la evaluación cualitativa con medición continua automatizada. El alumno debe entender que en la industria se usan AMBOS: rúbricas humanas (code review) + métricas automáticas (MI, complejidad). ISO 25010 es el estándar de calidad de software que referencia cualquier proceso formal.

### 6. [Conectar] La clase estructura la entrevista técnica con 10 ejercicios prácticos y 50 preguntas teóricas. ¿Qué es el método STAR (Situation, Task, Action, Result) para entrevistas de comportamiento y cómo se aplica para responder preguntas sobre experiencia con Clean Code que van más allá de las respuestas técnicas?

**Respuesta**: El método STAR es un marco para estructurar respuestas en entrevistas de comportamiento (behavioral interviews): Situation (contexto: "En el proyecto de payroll, teníamos un endpoint de cálculo que tardaba 30 segundos"), Task (mi responsabilidad: "Me asignaron optimizarlo refactorizando el código legacy"), Action (qué hice específicamente: "Apliqué extracción de métodos hasta reducirlos a <20 líneas, eliminé 3 queries duplicadas usando DRY, encapsulé cálculos en Value Objects con invariantes de negocio, escribí 45 characterization tests antes de tocar lógica"), Result (resultados medibles: "El endpoint bajó a 1.2 segundos, la cobertura de tests subió de 12% a 85%, y 0 bugs en producción en 6 meses"). La clase prepara al alumno para respuestas TÉCNICAS directas ("¿qué es SRP?"), pero en entrevistas reales, los entrevistadores preguntan "contame de una vez que aplicaste Clean Code" y evalúan profundidad de experiencia a través de STAR. Sin estructura STAR, el alumno responde con generalidades ("sí, siempre nombro bien las variables") que no demuestran experiencia real.

**Por qué**: La clase es puramente técnica. El método STAR es el estándar de la industria para entrevistas de comportamiento (usado en Amazon, Google, Meta para todos los niveles). El alumno que integra conocimiento técnico con estructura STAR es mucho más efectivo en entrevistas.

### 7. [Conectar] La clase pide cobertura > 80% como requisito del proyecto final. ¿Qué dice la investigación de Inozemtseva y Holmes (2014, ICSE) sobre la correlación entre cobertura de tests y defectos post-release? ¿Por qué "coverage is not a good measure of test suite quality" según este estudio?

**Respuesta**: Laura Inozemtseva y Reid Holmes (University of Waterloo, ICSE 2014, "Coverage Is Not Strongly Correlated with Test Suite Effectiveness") analizaron 5 proyectos open-source grandes (Eclipse, Tomcat, etc.) con más de 100 millones de líneas de código combinadas. Conclusión principal: la cobertura (line/branch coverage) tiene una CORRELACIÓN BAJA (r ≈ 0.2-0.3) con la efectividad real de los tests para detectar defectos. Los factores que SÍ correlacionan fuertemente: (a) la diversidad de datos de entrada en los tests (inputs variados), (b) el tamaño del suite de tests (número de tests, no líneas cubiertas), (c) la madurez del proyecto (proyectos más viejos con más tests tienden a tener menos bugs independientemente del % de cobertura). El estudio encontró que la cobertura es un proxy DÉBIL: un suite con 90% de cobertura generada por tests sin asserts es peor que un suite con 50% de cobertura con tests que verifican comportamiento. La implicancia: la clase pide >80% de cobertura como meta, pero esta meta es insuficiente (y potencialmente engañosa) sin verificar la CALIDAD de los tests a través de mutation testing o code review de tests.

**Por qué**: La clase usa cobertura como métrica principal de calidad de tests. El estudio de Inozemtseva & Holmes es la investigación más citada sobre las limitaciones de coverage. La conclusión: 80% es un mínimo necesario pero NO suficiente. El alumno debe entender que cobertura alta con tests malos es falsa seguridad.

### 8. [Cuestionar] La clase evalúa el proyecto con una rúbrica que asigna pesos a cada categoría. ¿Qué implicancias tiene pesar Tests 25% y Comentarios 5%? ¿Refleja esto las prioridades correctas según la investigación empírica de defectos, o es una valoración subjetiva de Robert C. Martin?

**Respuesta**: Los pesos de la rúbrica (Tests 25%, Funciones 15%, Errores 15%, Clases 15%, Nombres 10%, Adapters 10%, Comentarios 5%, Formato 5%) reflejan las prioridades SUBJETIVAS del diseño del curso. La pregunta es si la evidencia empírica las respalda: (a) Tests pesa 25% → consistente con la investigación: los estudios muestran que la presencia de una suite de tests robusta es el factor #1 en reducción de defectos (más predictivo que cualquier métrica de código), (b) Nombres pesa 10% → probablemente SUB-ponderado: el estudio de Buse & Weimer (2012) muestra que identificadores confusos son el principal factor que frena la legibilidad; Arnaoudova et al. encontraron que "linguistic anti-patterns" en nombres son predictores de bugs tan fuertes como la complejidad, (c) Comentarios pesa 5% → razonable porque Clean Code argumenta que buen código reduce la necesidad de comentarios, pero el estudio de Ibrahim et al. muestra que comentarios Javadoc en APIs públicas aportan valor medible, (d) Formato pesa 5% → subestimado: la consistencia de formato afecta la velocidad de lectura (Busjahn et al., eye-tracking), pero automatizar el formato con Spotless hace que el peso en la NOTA sea bajo porque se corrige solo. Una rúbrica mejor podría pesar Nombres más alto (15%) y reducir el peso combinado de Comentarios+Formato dado que las herramientas los automatizan.

**Por qué**: La rúbrica se presenta como objetiva, pero sus pesos son decisiones editoriales de Martin. El alumno debe desarrollar pensamiento crítico sobre las METODOLOGÍAS de evaluación que usará en su carrera, incluyendo cuestionar si los pesos asignados reflejan evidencia empírica o intuición del autor.

### 9. [Cuestionar] La clase lista 4 niveles de seniority (Junior, Semi-Senior, Senior, Tech Lead) con diferentes enfoques de evaluación. ¿Cómo se diferencian REALMENTE estos niveles en la industria según matrices de competencias como las de "Engineering Ladders" (progression.fyi, Dropbox, Square)? ¿En qué dimensión Clean Code diferencia niveles que la industria NO valora?

**Respuesta**: Matrices como progression.fyi (recopilación de ladders de 50+ empresas) y las de Dropbox/Spotify/Square definen niveles de seniority en 4 ejes: (a) Impacto (alcance del trabajo: componente → sistema → múltiples sistemas → organización), (b) Autonomía (necesita guía → independiente → guía a otros → define dirección), (c) Complejidad (tareas definidas → problemas ambiguos → define problemas → define estrategia), (d) Influencia (individual → equipo → múltiples equipos → industria). La rúbrica de la clase evalúa CALIDAD DE CÓDIGO (aplicar reglas → refactorizar → patrones → estándares), lo cual se alinea con el eje de Impacto pero ignora que la industria valora MUCHO más el eje de Influencia (mentoring, code reviews, diseño de procesos de equipo) en niveles altos. Un Senior que escribe código perfecto pero no mentorea juniors será evaluado como Semi-Senior en la mayoría de las empresas. La clase deja la impresión de que "aplicar más principios" = mayor seniority; la industria evalúa seniority por el radio de impacto y la capacidad de elevar al equipo.

**Por qué**: La clase conceptualiza seniority exclusivamente como dominio técnico de Clean Code. En la industria, un Senior es evaluado por la capacidad de hacer al EQUIPO más efectivo, no solo por escribir mejor código. El alumno debe entender esta diferencia para no sobredimensionar su nivel real basado solo en conocimiento técnico.

### 10. [Cuestionar] La clase presenta Clean Code como un conjunto de prácticas a aplicar y evaluar. ¿Qué argumenta el movimiento "Post-Clean Code" representado por autores como Casey Muratori ("Clean Code, Horrible Performance") o el artículo "Goodbye, Clean Code" de Dan Abramov? ¿Cuál es la crítica central sobre el costo en PERFORMANCE de algunas prácticas de Clean Code?

**Respuesta**: Casey Muratori, en su charla "Clean Code, Horrible Performance" (2023), argumenta que varias prácticas de Clean Code tienen un COSTO DE PERFORMANCE significativo que el libro ignora: (a) funciones pequeñas → cada llamada a función tiene overhead de stack frame, branch prediction y cache locality: en un loop de 10M de iteraciones, extraer el cuerpo a una función puede multiplicar x3 el tiempo de ejecución, (b) polimorfismo sobre switch → despacho virtual (vtable) es más lento que una tabla de saltos (switch), y en hot paths la diferencia es medible, (c) objetos pequeños con getters/setters → fragmentation de memoria (muchos objetos en heap en lugar de arrays contiguos) destruye la cache locality que CPUs modernas necesitan. Dan Abramov (creador de Redux, React core team) escribió "Goodbye, Clean Code" (2020) argumentando que la búsqueda de "código limpio" puede llevar a abstracciones innecesarias que oscurecen más de lo que revelan, citando ejemplos donde él mismo introdujo complejidad por seguir principios de Clean Code. La crítica no es "Clean Code es malo" sino "Clean Code optimiza para legibilidad humana y asume que la performance no importa —lo cual es cierto en CRUDs pero falso en sistemas de alto rendimiento, motores de juegos, o procesamiento de datos masivo".

**Por qué**: La clase no menciona trade-offs de performance. Muratori (Handmade Hero, ex-RAD Game Tools) y Abramov (React) representan comunidades donde la performance importa. El alumno debe entender que Clean Code es óptimo para la mayoría del software empresarial pero tiene contraindicaciones en dominios específicos. Un profesional maduro elige cuándo aplicar cada principio basado en los requerimientos del dominio, no aplica Clean Code como receta universal.
