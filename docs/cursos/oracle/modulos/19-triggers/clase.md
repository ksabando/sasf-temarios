# Módulo 14: Triggers y Consistencia del Modelo

## 1. ¿Qué es un Trigger?

Un **trigger** es un bloque PL/SQL que se ejecuta **automáticamente** cuando ocurre un evento DML (INSERT, UPDATE, DELETE) sobre una tabla o vista.

### Sintaxis

```sql
CREATE OR REPLACE TRIGGER nombre_trigger
    {BEFORE | AFTER | INSTEAD OF}
    {INSERT | UPDATE | DELETE} [OF columna]
    ON tabla_o_vista
    [FOR EACH ROW]
    [WHEN (condicion)]
    [FOLLOWS otro_trigger]
    [ENABLE / DISABLE]
DECLARE
    -- variables
BEGIN
    -- lógica
END;
/
```

## 2. Tipos de Triggers

### BEFORE / AFTER

| Timing | Uso típico |
|--------|------------|
| BEFORE | Validaciones, asignar valores default, calcular columnas derivadas |
| AFTER  | Auditoría, propagación a otras tablas, actualización de resúmenes |

### FOR EACH ROW vs Statement-Level

| Nivel | Se ejecuta | :OLD / :NEW |
|-------|------------|-------------|
| FOR EACH ROW | Una vez por fila afectada | Disponible |
| Statement-level | Una vez por sentencia SQL | No disponible |

Regla práctica: si necesitas `:OLD` o `:NEW`, es row-level (FOR EACH ROW).

## 3. :OLD y :NEW Pseudo-records

Son registros implícitos que representan los valores antes y después de la operación:

| Operación | :OLD | :NEW |
|-----------|------|------|
| INSERT | NULL (todos los campos NULL) | Valores insertados |
| UPDATE | Valores antes del cambio | Valores después del cambio |
| DELETE | Valores antes de eliminar | NULL (todos los campos NULL) |

```sql
CREATE OR REPLACE TRIGGER trg_control_horas
    BEFORE UPDATE OF horas_reales ON tareas
    FOR EACH ROW
BEGIN
    IF :NEW.horas_reales > :OLD.horas_estimadas * 1.5 THEN
        RAISE_APPLICATION_ERROR(-20100, 'Horas reales exceden el máximo permitido');
    END IF;
END;
/
```

## 4. WHEN Clause

Permite filtrar cuándo se ejecuta el trigger (solo en row-level):

```sql
CREATE OR REPLACE TRIGGER trg_estado_tarea
    BEFORE UPDATE OF estado ON tareas
    FOR EACH ROW
    WHEN (NEW.estado = 'C' AND OLD.estado != 'C')
BEGIN
    -- Solo cuando se completa una tarea
    DBMS_OUTPUT.PUT_LINE('Tarea ' || :NEW.id || ' completada');
END;
/
```

## 5. INSTEAD OF Triggers

Se usan sobre **vistas** no actualizables para permitir operaciones DML:

```sql
CREATE OR REPLACE VIEW v_proyecto_resumen AS
SELECT p.id, p.nombre,
       COUNT(t.id) AS total_tareas,
       SUM(t.horas_reales) AS horas_totales
FROM proyectos p
LEFT JOIN tareas t ON p.id = t.proyecto_id
GROUP BY p.id, p.nombre;

CREATE OR REPLACE TRIGGER trg_v_proyecto_resumen
    INSTEAD OF INSERT ON v_proyecto_resumen
    FOR EACH ROW
BEGIN
    INSERT INTO proyectos (id, nombre)
    VALUES (:NEW.id, :NEW.nombre);
END;
/
```

## 6. Triggers Compuestos (Oracle 12c+)

Combinan múltiples puntos de disparo en un solo trigger:

```sql
CREATE OR REPLACE TRIGGER trg_control_tiempo
    FOR UPDATE OF horas_reales ON tareas
    COMPOUND TRIGGER

    v_total_horas NUMBER := 0;

    BEFORE EACH ROW IS
    BEGIN
        IF :NEW.horas_reales > :OLD.horas_estimadas * 1.5 THEN
            RAISE_APPLICATION_ERROR(-20100, 'Excede máximo');
        END IF;
    END BEFORE EACH ROW;

    AFTER EACH ROW IS
    BEGIN
        v_total_horas := v_total_horas + (:NEW.horas_reales - NVL(:OLD.horas_reales, 0));
    END AFTER EACH ROW;

    AFTER STATEMENT IS
    BEGIN
        DBMS_OUTPUT.PUT_LINE('Total horas actualizadas: ' || v_total_horas);
    END AFTER STATEMENT;

END trg_control_tiempo;
/
```

## TABLE MODELING: Triggers como Guardianes del Modelo

### 1. Integridad del Modelo

Los triggers son el **último nivel de defensa** para la integridad de los datos. Mientras que:

- **CHECK constraints**: Validan una sola fila, una sola tabla, sin acceso a otras tablas.
- **FK constraints**: Garantizan integridad referencial básica.
- **TRIGGERS**: Pueden validar reglas que cruzan tablas, evaluar condiciones complejas y lanzar errores personalizados.

### 2. Validaciones Complejas

```sql
CREATE OR REPLACE TRIGGER trg_validar_asignacion
    BEFORE INSERT OR UPDATE OF responsable_id ON tareas
    FOR EACH ROW
DECLARE
    v_tareas_activas NUMBER;
BEGIN
    SELECT COUNT(*) INTO v_tareas_activas
    FROM tareas
    WHERE responsable_id = :NEW.responsable_id
      AND estado IN ('P', 'E')
      AND id != NVL(:NEW.id, -1);

    IF v_tareas_activas >= 5 THEN
        RAISE_APPLICATION_ERROR(-20101,
            'El empleado ya tiene ' || v_tareas_activas || ' tareas activas');
    END IF;
END;
/
```

### 3. Auditoría de Cambios

```sql
CREATE TABLE auditoria_tareas (
    id               NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tarea_id         NUMBER(10),
    campo_modificado VARCHAR2(50),
    valor_anterior   VARCHAR2(500),
    valor_nuevo      VARCHAR2(500),
    usuario          VARCHAR2(100),
    fecha            TIMESTAMP DEFAULT SYSTIMESTAMP
);

CREATE OR REPLACE TRIGGER trg_auditar_tareas
    AFTER UPDATE ON tareas
    FOR EACH ROW
BEGIN
    IF :OLD.estado != :NEW.estado THEN
        INSERT INTO auditoria_tareas (tarea_id, campo_modificado, valor_anterior, valor_nuevo, usuario)
        VALUES (:OLD.id, 'ESTADO', :OLD.estado, :NEW.estado, USER);
    END IF;

    IF :OLD.horas_estimadas != :NEW.horas_estimadas THEN
        INSERT INTO auditoria_tareas (tarea_id, campo_modificado, valor_anterior, valor_nuevo, usuario)
        VALUES (:OLD.id, 'HORAS_ESTIMADAS', TO_CHAR(:OLD.horas_estimadas), TO_CHAR(:NEW.horas_estimadas), USER);
    END IF;
END;
/
```

### 4. Sincronización de Tablas Derivadas

Mantener actualizados datos resumidos en la tabla padre:

```sql
ALTER TABLE proyectos ADD horas_totales NUMBER(8,1) DEFAULT 0;

CREATE OR REPLACE TRIGGER trg_sincronizar_horas
    AFTER INSERT OR UPDATE OR DELETE ON tareas
DECLARE
    TYPE t_proyecto_ids IS TABLE OF proyectos.id%TYPE;
    v_ids t_proyecto_ids;
BEGIN
    -- Solo si afectó horas_reales o proyecto_id
    IF UPDATING THEN
        SELECT DISTINCT :OLD.proyecto_id BULK COLLECT INTO v_ids FROM dual;
        INSERT INTO v_ids SELECT :NEW.proyecto_id FROM dual WHERE :NEW.proyecto_id IS NOT NULL;
    END IF;
    -- La implementación real usaría tablas temporales
NULL;
END;
/
```

### 5. Table API vs Triggers: ¿Cuándo usar cada uno?

| Escenario | Table API | Trigger |
|-----------|-----------|---------|
| Validación de reglas de negocio | ✅ Mejor | ⚠️ Backup |
| Auditoría | ✅ Posible | ✅ Ideal |
| Sincronización entre tablas | ✅ Posible | ✅ Ideal |
| REST API / aplicaciones externas | ✅ Necesario | ❌ No aplica |
| Operaciones por lote (BULK) | ✅ Controlable | ⚠️ Puede ser lento |

**Regla de oro**: La Table API es la primera línea de defensa. Los triggers son la **red de seguridad** que garantiza consistencia incluso si alguien hace INSERT directo.

### 6. Cuándo NO usar Triggers

- Para lógica que puede implementarse con CHECK o FK constraints.
- Para lógica de negocio compleja que debe ser visible y testeable (preferir procedures).
- En tablas con operaciones masivas (los triggers por fila impactan performance).
- Cuando el trigger depende de estado de sesión (contexto de aplicación) que podría no estar inicializado.
