### 2. [Investigar] ¿Cómo se relaciona SOLID con la metodología "Atomic Design" de Brad Frost (2013)? Investigá la jerarquía átomos → moléculas → organismos → templates → páginas y cómo cada nivel se alinea con SRP, ISP y OCP en componentes React.

**Respuesta**: Brad Frost propuso Atomic Design como metodología para construir interfaces. La relación con SOLID: **Átomos** (button, input, label): son componentes de una sola responsabilidad (SRP puro). Cada átomo recibe props mínimas (ISP). Variaciones de un átomo se logran con props, no con herencia (OCP: `variant="primary" | "secondary"` en lugar de `PrimaryButton extends Button`). **Moléculas** (SearchBar = input + button): componen átomos, cada molécula tiene una responsabilidad compuesta (SRP a nivel de molécula). No heredan de átomos — composición pura (LSP no aplica). **Organismos** (Header = logo + nav + searchbar): orquestan moléculas, se comportan como "componentes contenedor" en React. **Templates**: layout sin datos reales — ISP a nivel de página (no reciben datos que no renderizan). **Páginas**: templates con datos reales, donde se inyectan servicios (DIP a nivel de página). Atomic Design implementa SOLID en el frontend: cada nivel tiene una responsabilidad definida, las interfaces entre niveles son props (ISP), la extensión se hace por composición (OCP), y los servicios se inyectan en las páginas (DIP). La jerarquía fuerza a pensar en granularidad de responsabilidades — un átomo no puede ser un organismo, y viceversa.

**Por qué**: Frost no diseñó Atomic Design con SOLID en mente, pero hay un isomorfismo natural: SRP produce átomos cohesivos, ISP produce átomos con props mínimas, OCP produce moléculas extensibles por composición. La metodología de Frost es una implementación práctica de SOLID en diseño de UI.

### 3. [Investigar] React Server Components (RSC, 2023) introducen un nuevo modelo de ejecución donde los componentes pueden ser exclusivamente del servidor. ¿Cómo afecta esto a los principios SOLID, especialmente SRP y DIP? ¿Quién es el "actor" que puede solicitar cambios en un Server Component vs un Client Component?

**Respuesta**: RSC divide los componentes en dos categorías con modelos de ejecución diferentes: **Server Components**: se ejecutan solo en el servidor, pueden acceder a BD y sistema de archivos directamente, no tienen estado interactivo. **Client Components**: se ejecutan en el navegador, tienen estado, efectos y eventos. Impacto en SOLID: **SRP**: RSC fuerza una separación de responsabilidades radical: los componentes de datos (server) y los componentes interactivos (client) son naturalmente segregados. Un Server Component `UserProfile` que obtiene datos de la BD tiene un solo actor (backend/data team). Un Client Component `UserProfileEditor` que maneja interacción tiene otro actor (UX team). La línea "use client" es un marcador de SRP explícito. **DIP**: los Server Components pueden acceder directamente a BD sin abstracciones (fetch desde el servidor no requiere mock para tests), lo que PARECE violar DIP pero en realidad la "dependencia de infraestructura" es natural porque el servidor ES infraestructura. Para testing, se mockea la capa de datos (server actions), no el componente. **ISP**: los Server Components típicamente retornan datos serializados (solo props), lo que naturalmente produce interfaces mínimas. **OCP**: RSC + Server Actions permiten agregar nuevas operaciones al servidor sin modificar componentes cliente existentes. En resumen, RSC hace que SRP y DIP sean más naturales porque el entorno de ejecución fuerza la separación de responsabilidades y la inversión de dependencias es inherente (el cliente no sabe cómo el servidor obtiene los datos).

**Por qué**: El equipo de React (Dan Abramov, Andrew Clark) diseñó RSC para resolver problemas de waterfall de datos y bundle size, pero incidentalmente produjo una arquitectura más alineada con SOLID: la separación server/client es una separación por "actor" (SRP), y la comunicación es por props serializadas (ISP).

### 4. [Investigar] ¿Cómo implementa el framework SolidJS (Ryan Carniato, 2018) los principios de reactividad fina, y qué relación tiene esto con SOLID? ¿Es una coincidencia que se llame "Solid" o hay una filosofía de diseño detrás?

**Respuesta**: SolidJS no se llama así por SOLID, sino por el principio de "solid reactivity" (reactividad sólida/precisa). Sin embargo, hay alineaciones filosóficas: **SRP**: SolidJS fomenta "primitives" (createSignal, createEffect, createResource) como unidades atómicas de reactividad. Cada primitive tiene una responsabilidad única, a diferencia de React donde `useEffect` puede hacer múltiples cosas. **OCP**: el modelo de "stores" de Solid (createStore) con proxies permite extender el estado sin modificar componentes. Los componentes son funciones puras que reciben props. **DIP**: Solid no tiene un contenedor IoC, pero su ecosistema fomenta pasar "primitives" como dependencias — `function UserList({ getUserList })` donde `getUserList` es una función, no una implementación concreta. **LSP**: como no hay herencia de clases (todo son funciones), LSP se manifiesta en que cualquier función que cumpla la firma esperada es sustituible — tipado estructural, no nominal. **ISP**: los componentes reciben solo las props que usan (fine-grained reactivity: si una prop no se usa, no se re-renderiza). La conexión real con SOLID: SolidJS fue diseñado con los principios de "composición sobre herencia" y "reactividad declarativa", que son congruentes con SOLID aunque no fue explícitamente inspirado por Martin. El nombre es coincidencia, pero la filosofía de diseño subyacente converge.

**Por qué**: Ryan Carniato ha hablado sobre patrones de diseño en SolidJS (en su blog y charlas). Aunque no usa el vocabulario SOLID explícitamente, los principios de reactividad fina, composición declarativa y separación de responsabilidades son análogos funcionales a SRP, OCP y DIP.

### 5. [Conectar] La clase muestra React Context + custom hooks como implementación de DIP. Investigá el patrón "Functional Core, Imperative Shell" (Gary Bernhardt, 2012) y explicá cómo se relaciona con DIP y SRP en aplicaciones React.

**Respuesta**: "Functional Core, Imperative Shell" (Bernhardt, "Boundaries", 2012) propone dividir la aplicación en: **Functional Core**: lógica pura — funciones que reciben datos y retornan decisiones, sin efectos secundarios. Todo es determinista y testeable sin mocks. **Imperative Shell**: capa externa que realiza efectos secundarios (HTTP, localStorage, DOM) y llama al functional core con los datos obtenidos. La relación con DIP en React: (1) El Functional Core ES la abstracción (DIP): define qué operaciones necesita (interfaces/promesas). (2) El Imperative Shell ES la implementación concreta (DIP): implementa las operaciones reales. (3) En un componente React, los hooks serían el Imperative Shell (llaman al functional core con datos y despachan resultados). Ejemplo: `function calculateDiscount(order: Order): number` (Functional Core, SRP puro). El hook `useOrder()` (Imperative Shell) obtiene la orden vía fetch, llama a `calculateDiscount`, y retorna el resultado. El componente solo renderiza. Conexión con SRP: Functional Core tiene una sola responsabilidad (cálculo puro). Imperative Shell tiene una sola responsabilidad (manejar efectos). El componente tiene una sola responsabilidad (renderizar). Es SRP + DIP integrados: el módulo de alto nivel (Functional Core) no depende de infraestructura; el módulo de bajo nivel (Imperative Shell) implementa las operaciones.

**Por qué**: Bernhardt presentó este patrón como una arquitectura para testeabilidad, y es directamente análogo a DIP: la lógica de negocio (= abstracción) no depende de efectos secundarios (= detalles). En React, esto se traduce a hooks como shell, funciones puras como core.

### 6. [Conectar] Relacioná los Render Props y Higher-Order Components (HOCs) que se mencionan en clase con el principio OCP. ¿Son los HOCs la aplicación de OCP en React mediante decoración? ¿Por qué la comunidad React migró de HOCs a hooks para implementar extensibilidad?

**Respuesta**: Ambos implementan OCP: (1) **HOCs**: `withAuth(MyComponent)` envuelve un componente agregando comportamiento de autenticación sin modificar `MyComponent` — el componente original está cerrado, el HOC extiende. El patrón Decorator llevado a React. (2) **Render Props**: `<DataFetcher url="/api/users" render={(data) => <UserList data={data} />} />` — `DataFetcher` está cerrado, el render prop extiende. ¿Por qué la migración a hooks? (a) **Wrapper hell**: múltiples HOCs anidados (`withAuth(withTheme(withRouter(MyComponent)))`) producen jerarquías difíciles de depurar y props que vienen "de la nada". (b) **Nombres de props colisionan**: dos HOCs pueden inyectar props con el mismo nombre. (c) **Static composition**: los HOCs se aplican en tiempo de definición, no en runtime. Los hooks permiten composición dinámica dentro del componente. (d) **SRP más claro**: un hook tiene una responsabilidad (`useAuth()`), un HOC puede mezclar varias (inconveniente para SRP). Los hooks implementan OCP de forma más granular: en lugar de envolver el componente, el componente compone hooks usando los que necesita. `function Dashboard() { const auth = useAuth(); const theme = useTheme(); ... }` — cada hook es una extensión que se agrega al componente sin modificar su estructura de props. La migración HOC → hooks es OCP + ISP: los hooks son role interfaces (ISP), mientras los HOCs eran header interfaces (inyectaban todas las props juntas).

**Por qué**: La comunidad React (Dan Abramov, Sophie Alpert) identificó que HOCs violaban ISP indirectamente al mezclar props inyectadas. Los hooks resuelven esto: cada hook expone una interfaz específica (ISP), y el componente elige exactamente qué hooks usar (OCP por composición).

### 7. [Conectar] ¿Cómo se relaciona SOLID con el patrón "Container/Presentational" de Dan Abramov (2015)? Este patrón separaba componentes en "containers" (lógica) y "presentational" (UI). ¿Es esto SRP aplicado a React? ¿Por qué Abramov luego dijo que este patrón está obsoleto con la llegada de hooks?

**Respuesta**: Abramov propuso en 2015 separar componentes en dos tipos: **Container Components**: manejan lógica (fetching, estado, cálculos) y pasan datos a presentacionales. **Presentational Components**: reciben props y renderizan UI. Esto es SRP puro: un componente tiene una sola responsabilidad (presentar o contener). Un container puede tener múltiples razones para cambiar (si maneja lógica de múltiples fuentes), pero al menos la separación básica está hecha. Abramov declaró este patrón obsoleto con hooks (2019) porque: (a) Los hooks permiten que cualquier componente funcional tenga estado y efectos sin ser una clase. La distinción container/presentational era en parte una necesidad técnica (class components vs functional stateless components). (b) Con hooks, un componente puede ser "presentational" y usar `useContext` sin convertirse en "container". (c) La tendencia actual es "un hook por responsabilidad" — cada hook encapsula una lógica; el componente compone hooks y renderiza. Esto es un refinamiento de SRP: en lugar de "containers grandes que manejan toda la lógica", tenés "hooks pequeños que manejan una responsabilidad cada uno". La relación con SOLID: Container/Presentational = SRP grueso (1 container con N responsabilidades). Hooks = SRP fino (N hooks con 1 responsabilidad cada uno). La evolución muestra que la comunidad React refinó SRP a granularidad más fina con hooks.

**Por qué**: Abramov explicó esta evolución en su blog overreacted.io (2019). Los hooks no invalidan SRP; lo refinan. La separación de responsabilidades sigue siendo el objetivo, pero la unidad de separación pasó de "componente" a "hook".

### 8. [Cuestionar] ¿Tiene sentido aplicar SOLID en React, un paradigma funcional con composición de funciones? Investigá la postura de desarrolladores que argumentan que SOLID es un "olor a OOP" forzado en React y que los patrones funcionales (composición, currying, HOF) ya resuelven los mismos problemas sin el vocabulario SOLID.

**Respuesta**: Críticos como Michel Weststrate (creador de MobX) y Eric Elliott argumentan que: (1) **SRP = funciones pequeñas**: la programación funcional ya tiene el principio de "funciones pequeñas que hacen una sola cosa". No necesitás SRP; necesitás "small pure functions". (2) **OCP = higher-order functions**: en lugar de crear una interfaz `Strategy` con implementaciones, pasá una función. OCP en FP es trivial: `const result = calculate(fn, data)`. La estrategia es `fn`. (3) **LSP = type system**: el tipado estructural de TypeScript garantiza sustituibilidad sin herencia. Si un objeto tiene `fly(): void`, es sustituible — no necesita una jerarquía de clases. (4) **ISP = props typing**: TypeScript ya fuerza que cada componente declare exactamente las props que necesita — ISP está en el sistema de tipos, no en el diseño. (5) **DIP = dependency injection via closures**: en lugar de inyectar una interfaz, inyectás una función. El closure captura la implementación concreta. La crítica es que SOLID trae vocabulario y patrones OOP (interfaces, herencia, polimorfismo) a un ecosistema que ya tiene soluciones funcionales más simples. **Defensa**: SOLID como principios (no como implementación OOP) sí aplican a React. SRP como "un hook = una responsabilidad", OCP como "componentes extensibles por composición", DIP como "hooks que reciben funciones en lugar de llamar a fetch". El error es copiar la implementación OOP (interfaces, Strategy Pattern con clases) en lugar de aplicar la INTENCIÓN de SOLID con herramientas funcionales (hooks, HOF, closures).

**Por qué**: Weststrate y Elliott no están en contra de los objetivos de SOLID (bajo acoplamiento, alta cohesión, extensibilidad). Están en contra del mecanismo OOP para lograrlos en un paradigma funcional. React + TypeScript permiten cumplir los objetivos de SOLID con menos ceremonias usando el sistema de tipos y funciones.

### 9. [Cuestionar] ¿Conducen los "custom hooks" a una explosión de abstracciones que viola YAGNI y complica el código sin beneficio? Investigá el fenómeno de "over-hooking" donde cada pequeña lógica se convierte en un hook reusable que solo se usa una vez.

**Respuesta**: El "over-hooking" es un anti-patrón React documentado por Kent C. Dodds y otros: crear `useUserName(user)` (1 línea de código), `useUserEmail(user)` (1 línea), etc., para cumplir SRP/ISP dogmáticamente. Los problemas: (1) **Explosión de archivos**: 30 hooks en 30 archivos que antes eran 30 líneas en un componente. (2) **Indirección innecesaria**: seguir el flujo de datos requiere saltar entre 10 archivos de hooks. (3) **YAGNI**: hooks creados "por si se reutilizan" y nunca reutilizados. (4) **Falsa cohesión**: hooks que parecen cohesivos por nombre pero que en realidad son un solo caso de uso fragmentado artificialmente. **Límite saludable según la comunidad**: (a) extraé un hook cuando la lógica tiene AL MENOS 10 líneas y es no trivial (fetching, cálculos, suscripciones). (b) Extraé cuando el hook SE REUTILIZA en al menos 2 componentes. (c) No extraigas cuando el hook solo envuelve un `useState` (1 línea de indirección no justifica un archivo). (d) El test: ¿si muevo esta lógica a un hook, puedo probarla aisladamente? Si la respuesta es no (porque la lógica solo tiene sentido en el contexto del componente), no la extraigas. Kent C. Dodds: "un hook no es un refugio para cualquier lógica; es una abstracción. Y las abstracciones tienen un costo".

**Por qué**: La comunidad React pasó de "todo en el componente" (2016) a "todo en hooks" (2019) y ahora se estabiliza en un equilibrio (2023+). La regla de Dodds "colocate until it hurts" (mantené la lógica junta hasta que duela la duplicación) es la antítesis del over-hooking dogmático.

### 10. [Cuestionar] ¿Es el Context API de React realmente DIP o es un "Service Locator" glorificado? Compará con la inyección por props (prop drilling) y evaluá si Context API introduce acoplamiento implícito que viola DIP de una forma diferente a la que resuelve.

**Respuesta**: Context API está más cerca de un Service Locator que de Dependency Injection verdadera. Argumentos: (1) **Dependencia implícita**: `const userService = useContext(UserContext)` — la dependencia no está declarada en los props del componente. No podés saber qué necesita el componente mirando su firma. Esto es EXACTAMENTE la crítica que se le hace a Service Locator. (2) **Acoplamiento al Context**: el componente se acopla al Context específico (no a una interfaz general). Si cambiás `UserContext` por `AuthContext`, tenés que modificar el componente. Con DI verdadera (inyección por props), el componente recibe el servicio sin saber de dónde viene. (3) **Testing**: necesitás envolver el componente en un Provider para testearlo — igual que necesitás configurar un Service Locator. Con inyección por props, pasás el mock directamente. **Pero Context API también tiene ventajas sobre Service Locator tradicional**: (a) El acoplamiento es explícito en el árbol de componentes (el Provider es visible en el JSX). (b) TypeScript tipa el contexto — no hay búsqueda por string como en Service Locator clásico. (c) Podés tener múltiples Providers del mismo tipo en diferentes partes del árbol. **Comparación**: Prop drilling = DI verdadera (dependencias explícitas, visibles en props). Context API = Service Locator mejorado (dependencias implícitas pero type-safe). El DIP ideal en React sería: el componente recibe el servicio por props (DI), y el padre lo obtiene del Context (Service Locator localizado en el padre). Así el componente es DIP puro (depende de la abstracción inyectada) y el padre se encarga del wiring.

**Por qué**: La comunidad React debate esto activamente. Dan Abramov reconoce que Context es "DI para el árbol de componentes", pero advierte contra usarlo para todo. La inyección por props hace DIP explícito; Context lo hace conveniente pero menos visible.
