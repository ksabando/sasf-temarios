### 2. [Investigar] ¿Cómo maneja Spring Modulith (2022, Oliver Drotbohm) la aplicación de SOLID a nivel de módulos en aplicaciones Spring Boot grandes? ¿Qué problemas de SOLID resuelve que el Spring tradicional no aborda?

**Respuesta**: Spring Modulith es un toolkit para estructurar aplicaciones Spring Boot en módulos con verificación de acoplamiento. Resuelve problemas SOLID que Spring tradicional no cubre: (1) **SRP/CCP a nivel de módulo**: Spring fomenta SRP a nivel de clase (@Controller, @Service, @Repository) pero no impide que una aplicación tenga un módulo `core` con 200 servicios mezclados. Modulith introduce el concepto de "módulo de aplicación" con `@ApplicationModule` y verifica que las dependencias entre módulos cumplan DIP (no dependencias cíclicas). (2) **ISP entre módulos**: Modulith permite definir `@ApplicationModule.NamedInterface` — interfaces públicas explícitas del módulo, análogo a ISP a nivel de módulo (los módulos solo exponen métodos que los consumidores necesitan). (3) **DIP entre módulos**: las pruebas de Modulith verifican que los módulos dependan de interfaces, no de implementaciones internas de otros módulos. (4) **OCP con eventos de módulo**: Modulith promueve comunicación entre módulos vía eventos (Spring ApplicationEvent), cumpliendo OCP — un módulo emite eventos sin conocer a los consumidores. (5) **Verificación arquitectónica automatizada**: tests de `Modulith.verify()` que validan que no haya dependencias prohibidas, ciclos, o accesos a tipos internos — fallando el build si se violan. Esto lleva SOLID de "principios de clase" a "principios arquitectónicos verificables".

**Por qué**: Drotbohm creó Modulith porque observó que Spring Boot no protege contra el acoplamiento entre paquetes. Un `@Service` puede inyectar cualquier otro `@Service` de cualquier paquete. Modulith agrega la capa de verificación que SOLID necesita a nivel de módulo: DIP entre módulos, ISP de API de módulo, SRP de módulo.

### 3. [Investigar] ¿Cómo influye Spring AOP en el cumplimiento de SRP? Investigá el debate sobre si los aspectos (logging, transacciones, seguridad) "inyectados" mediante AOP son una forma de mantener SRP (la lógica transversal no contamina la clase) o una forma de violarlo (la clase tiene responsabilidades ocultas que solo se revelan con configuración externa).

**Respuesta**: Debate con dos posturas: **A favor de AOP + SRP**: Ramnivas Laddad ("AspectJ in Action", 2003) argumenta que AOP es la ÚNICA forma de cumplir SRP para preocupaciones transversales (cross-cutting concerns). Una clase `OrderService` con `@Transactional` NO contiene código de transacción, solo la anotación. La lógica real está en el aspecto (TransactionInterceptor). La clase cumple SRP (lógica de negocio), y el aspecto cumple su propia SRP (gestión de transacciones). Sin AOP, el código de transacción se mezclaría en la clase. **En contra de AOP + SRP**: Kevlin Henney señala que AOP oculta responsabilidades, violando el "principio de menor sorpresa". La clase `OrderService` TIENE responsabilidades (transaccionalidad, logging, seguridad) que no son visibles en su código fuente. Un desarrollador que lee `OrderService` no sabe que tiene transacciones, logs y autorización — responsabilidades que existen pero son invisibles. Esto es una violación SRP "oculta": la clase responde a múltiples actores (negocio, seguridad, operaciones) pero no se ve en el código. La solución híbrida: usar AOP para infraestructura pura (logging, métricas, tracing — no afectan el comportamiento del negocio), pero mantener lógica de dominio explícita en la clase (validación, reglas de negocio). Gregory Kick (Google) propone: "si un aspecto cambia el comportamiento observable del negocio, no debería ser un aspecto".

**Por qué**: El debate es si SRP aplica al código fuente o al comportamiento en runtime. Martin no abordó AOP explícitamente en SOLID porque AspectJ (2001) es posterior. La comunidad está dividida: AOP es necesario para preocupaciones transversales, pero su opacidad es un riesgo.

### 4. [Investigar] ¿Cómo se relaciona SOLID con el patrón "Spring Data REST"? Investigá cómo Spring Data REST aplica ISP automáticamente (exponiendo solo operaciones CRUD según el repositorio) pero puede violar otros principios SOLID si no se configura adecuadamente.

**Respuesta**: Spring Data REST (Oliver Gierke, Roy Clarkson) expone repositorios Spring Data directamente como recursos REST. **Cumple ISP automáticamente**: si un repositorio extiende solo `CrudRepository`, la API REST solo expone GET, POST, PUT, DELETE. Si extiende `PagingAndSortingRepository`, se agregan parámetros de paginación. Si extiende `JpaRepository`, se exponen más operaciones. Cada repositorio define exactamente qué se expone. **Puede violar otros principios**: (1) **SRP**: un solo repository expuesto como REST puede mezclar responsabilidades de consulta y comando — es mejor separar `BookReader` (expuesto como GET) y `BookWriter` (expuesto como POST/PUT). (2) **DIP**: el controller generado automáticamente depende directamente de `BookRepository` como interfaz Spring Data (que es una abstracción de Spring, no del dominio). Si se quiere cambiar de Spring Data a otro mecanismo, hay que modificar el modelo REST. (3) **OCP**: las URLs y representaciones son generadas, no diseñadas. Cambiar el modelo de datos cambia la API automáticamente — potencialmente rompiendo clientes. Las buenas prácticas: usar Spring Data REST para prototipos o APIs internas, pero no para APIs públicas estables. Para APIs públicas, crear controladores explícitos que mapeen repositorios ISP-segregados a endpoints diseñados manualmente (control sobre la API incluso si el modelo cambia).

**Por qué**: Roy Clarkson y Oliver Gierke diseñaron Spring Data REST como un acelerador, no como un sustituto del diseño de APIs. La comunidad recomienda "API-first design" donde los repositorios ISP se usan internamente, pero los endpoints externos se diseñan por contrato.

### 5. [Conectar] Relacioná la arquitectura de capas de Spring con la "Clean Architecture" de Robert C. Martin. ¿En qué se diferencian la "capa de servicio" tradicional de Spring y el "caso de uso" (use case / interactor) de Clean Architecture? ¿Promueve Spring la misma separación que Clean Architecture?

**Respuesta**: Diferencia fundamental: **Spring tradicional**: capas horizontales — `Controller` (HTTP) → `Service` (lógica de negocio) → `Repository` (datos). El `Service` es una capa genérica que típicamente contiene TODOS los casos de uso mezclados: `UserService.createUser()`, `UserService.deleteUser()`, `UserService.findUser()`. **Clean Architecture**: capas verticales — cada caso de uso es una clase separada: `CreateUserInteractor`, `DeleteUserInteractor`, `FindUserInteractor`. Cada interactor implementa un "Input Boundary" (interfaz que el controller llama). Spring no impone Clean Architecture porque: (1) La convención `@Service` fomenta servicios por entidad, no por caso de uso — SRP a nivel de entidad, pero múltiples razones para cambiar dentro del mismo servicio. (2) Los controladores Spring típicamente inyectan `UserService` (con todos los métodos), no `CreateUserInputBoundary` (solo un método). (3) Spring no tiene anotación para "caso de uso" (@UseCase) — el concepto no existe en el framework. **Se puede lograr Clean Architecture en Spring**: usar `@Service` para cada interactor individual, inyectar interfaces de Input Boundary en los controllers, y usar DIP para que el controller no conozca la implementación. Pero requiere disciplina manual; Spring no lo promueve por defecto.

**Por qué**: Martin diseñó Clean Architecture como evolución de la arquitectura en capas tradicional. Spring implementa la versión tradicional. La diferencia es de granularidad SRP: "un servicio por entidad" (Spring tradicional) vs "un caso de uso por clase" (Clean Architecture).

### 6. [Conectar] ¿Cómo se puede verificar arquitectónicamente el cumplimiento de SOLID en una aplicación Spring Boot usando ArchUnit? Investigá y mostrá cómo un test de ArchUnit puede detectar violaciones de DIP, ISP y OCP automáticamente en el CI/CD, yendo más allá de lo que SonarQube puede hacer.

**Respuesta**: ArchUnit (Stefan Gaul, 2017) permite escribir tests de arquitectura que verifican reglas de dependencia. Ejemplos de verificación SOLID: **DIP**: `classes().that().resideInAPackage("..service..").should().dependOnClassesThat().resideInAPackage("..infrastructure..").check(classes)` — detecta si un servicio depende de infraestructura concreta (viola DIP). **ISP**: `classes().that().implement(SomeService.class).should().haveOnlyFinalFields().andShould().beAnnotatedWith(Service.class)` — detecta interfaces infladas si la implementación tiene campos no usados. **OCP**: `classes().that().resideInAPackage("..strategy..").should().implement(Strategy.class).andShould().haveSimpleNameEndingWith("Strategy")` — verifica que nuevas estrategias sigan la convención. **SRP**: `methods().that().areAnnotatedWith(Scheduled.class).should().beDeclaredInClassesThat().resideOutsideOfPackage("..service..")` — garantiza que jobs programados no estén en servicios de negocio. Además, ArchUnit verifica: ciclos de dependencia entre paquetes (violan SDP), acceso a clases internas de otros módulos (violan encapsulamiento), y dependencias hacia paquetes prohibidos (ej. ningún controller debe depender de `java.sql`). Comparado con SonarQube (análisis estático por archivo), ArchUnit analiza relaciones entre clases y paquetes — es la herramienta para detectar violaciones SOLID a nivel arquitectónico, no solo de clase. Integrado en CI/CD: cualquier violación rompe el build.

**Por qué**: ArchUnit es la materialización de la verificación arquitectónica que Martin recomienda. Los tests de arquitectura son la única forma de garantizar que SOLID se mantenga en el tiempo sin depender de revisión manual.

### 7. [Conectar] Conectá el uso de `@EventListener` y `ApplicationEventPublisher` de Spring con el principio OCP. ¿Cómo el sistema de eventos de Spring permite extender el comportamiento del sistema sin modificar código existente? Compará con el ejemplo de Strategy de la clase.

**Respuesta**: El sistema de eventos de Spring implementa OCP a través del patrón Observer: cuando un módulo publica un evento (`publisher.publishEvent(new OrderPlacedEvent(order))`), múltiples listeners pueden reaccionar sin que el publicador los conozca. Para agregar comportamiento nuevo (ej. enviar notificación por WhatsApp cuando se crea una orden), se crea un `@EventListener` nuevo — el `OrderService` no se modifica. Comparación con Strategy: **Strategy** es OCP síncrono (el servicio conoce la interfaz de estrategia y la llama directamente). **Eventos** es OCP asíncrono (el servicio NO conoce a los listeners; solo publica eventos). Estrategia requiere que el punto de extensión esté PRE-definido (interfaz `NotificationChannel`). Eventos permite extensión POST-definida (cualquier módulo puede escuchar eventos sin que el módulo origen fuera diseñado para ser extendido). Eventos es más flexible para extensiones imprevistas; Strategy es más adecuado para variaciones previstas del mismo algoritmo. Ejemplo: Strategy para cálculo de impuestos (variaciones previstas del mismo algoritmo). Eventos para acciones desencadenadas por "orden creada" (notificar, auditar, actualizar inventario, enviar email, generar factura — extensiones que aparecerán en el futuro). El publisher solo sabe que una orden fue creada; no sabe cuántas cosas pasarán como consecuencia. Esto es OCP en su máxima expresión: el módulo "orden" está cerrado a modificación pero infinitamente abierto a extensión vía listeners.

**Por qué**: Spring Events es la implementación de Observer con esteroides. OCP dice "abierto a extensión, cerrado a modificación"; eventos dice "no te modificaré, pero escucharé todo lo que publiques, y podrás agregar listeners sin tocarme".

### 8. [Cuestionar] ¿Fomenta Spring Boot las "anemic domain models" (modelos de dominio anémicos) que son anti-SOLID? Investigá cómo la típica estructura Spring (Entity + DTO + Repository + Service + Controller) tiende a producir objetos sin comportamiento y lógica en servicios, y cómo esto se relaciona con las críticas de Martin Fowler sobre modelos anémicos.

**Respuesta**: Spring Boot, por convención y por la separación de capas, TIENDE a producir modelos anémicos: las entidades JPA (`@Entity`) son POJOs con getters/setters y cero lógica de dominio. Toda la lógica está en `@Service`. Esto es exactamente lo que Martin Fowler describió como "anemic domain model anti-pattern" en 2003. La relación con SOLID: (1) **SRP invertido**: en lugar de que el objeto `Order` tenga la responsabilidad de calcular su total, validar sus ítems, y verificar si es modificable, esas responsabilidades están dispersas en `OrderService`, `OrderValidator`, `OrderCalculator`. La cohesión del dominio se pierde. (2) **DIP redundante**: se crean interfaces `OrderService` y `OrderServiceImpl` cuando la lógica podría estar en `Order` directamente. (3) **Feature Envy**: los servicios están llenos de métodos que operan sobre datos de las entidades — el code smell clásico de "el servicio envidia los datos de la entidad". **Defensa**: Vaughn Vernon ("Implementing DDD", 2013) argumenta que en arquitecturas DDD con Spring, las entidades pueden ser ricas (con lógica de dominio) y los servicios de aplicación solo coordinan. Spring no impide modelos ricos; la convención y los tutoriales sí. La estructura `Entity + DTO + Repository + Service + Controller` es una arquitectura procedural disfrazada de OOP. Para evitarlo: poner lógica de dominio en las entidades/aggregates, usar servicios de dominio solo para lógica que involucra múltiples aggregates, y usar servicios de aplicación solo como orquestadores delgados.

**Por qué**: Martin Fowler y Eric Evans advirtieron sobre modelos anémicos décadas antes de Spring Boot. Spring no fuerza el anti-patrón pero lo normaliza porque la mayoría de tutoriales y starters usan entidades sin comportamiento.

### 9. [Cuestionar] Investigá la crítica de que "Spring Boot es magia que oculta violaciones SOLID". ¿Es la inyección de dependencias implícita (component scanning, @Autowired en runtime) una ayuda o un obstáculo para entender y refactorizar el código según SOLID?

**Respuesta**: La crítica "Spring es magia" (popularizada por Oliver Gierke y otros) sostiene que: (1) **Dependencias ocultas**: `@Autowired` en campo o incluso `@Service` con component scanning hace que las dependencias no sean visibles — no sabés cuántas instancias de `UserService` hay ni quién las inyecta sin IDE o runtime. (2) **Violaciones DIP enmascaradas**: podés inyectar `JdbcTemplate` directamente en un `@Service` y el código compila y funciona — Spring no te advierte que estás violando DIP. (3) **Refactorización riesgosa**: renombrar un bean o cambiar su paquete puede romper la aplicación en runtime porque el component scanning lo deja de encontrar — sin error de compilación. (4) **Magia de AOP**: `@Transactional`, `@Cacheable`, `@Async` funcionan por proxies — el código que ves no es el que se ejecuta. Esto viola el principio de "least surprise" y hace que SOLID sea más difícil de verificar visualmente. **Defensa de Spring**: (a) Constructor injection (desde Spring 4.3+) elimina parte de la "magia" — las dependencias son explícitas. (b) `@SpringBootTest` con `@MockBean` facilita pruebas incluso con magia. (c) Spring Boot Actuator expone el grafo de beans en runtime para debugging. (d) La "magia" es productividad: menos boilerplate. El balance: usar component scanning para lo que es estable (infraestructura), pero ser explícito (configuración manual con @Bean) para dependencias de dominio, donde la claridad es más importante que la productividad de escritura.

**Por qué**: La comunidad Spring evolucionó hacia "explicit over magic": constructor injection por defecto, @Configuration classes con @Bean explícitos sobre component scanning para lógica de dominio. El balance es pragmático: magia para infraestructura repetitiva, explicit para lógica de negocio.

### 10. [Cuestionar] ¿Qué principios SOLID sacrifica un microservicio Spring Boot típico que usa Spring Data REST + Lombok + MapStruct + @Transactional en servicios? Investigá cómo la "pila de productividad" de Spring puede producir código que funciona pero que acumula violaciones SOLID invisibles.

**Respuesta**: La pila típica "productiva" produce violaciones sutiles: **Lombok** (`@Data`, `@AllArgsConstructor`): genera getters, setters, equals, hashCode, toString automáticamente. Viola encapsulamiento (ISP a nivel de clase: todos los campos son accesibles, incluso los que ningún cliente debería ver). **MapStruct** (`@Mapper`): genera código de mapeo Entity ↔ DTO. Tiende a producir DTOs "planos" que reflejan exactamente la estructura de la entidad — el DTO no es una abstracción (ISP/DIP: el cliente recibe la estructura interna de la entidad). **Spring Data REST**: expone repositorios como API. Un cambio en la entidad (agregar campo) se refleja automáticamente en la API — rompiendo el contrato con clientes (viola OCP: la API debería ser estable, no acoplada al modelo de datos). **@Transactional en servicios**: acopla la lógica de negocio a la infraestructura de transacciones (DIP: el servicio sabe que hay una BD transaccional). **Generación automática**: la productividad a corto plazo oculta que el código es frágil a cambios. Una nueva columna en la BD → cambia la entidad → Lombok regenera equals/hashCode (posiblemente rompiendo colecciones) → MapStruct regenera DTOs → Spring Data REST expone el nuevo campo → clientes externos lo reciben sin esperarlo. La pila "productiva" ahorra escritura pero multiplica el costo de cambio. La disciplina SOLID en este stack implica: DTOs diseñados manualmente (no generados), repositorios con proyecciones específicas (no exponer entidad completa), @Transactional solo en capa de infraestructura (no en dominio), y APIs con contratos explícitos (no auto-generadas).

**Por qué**: La pila Lombok + MapStruct + Spring Data REST es el epítome del "desarrollo rápido" que Martin advertía: funciona para prototipos pero se vuelve inmantenible a escala. SOLID es la disciplina que contrarresta la entropía de la generación automática.
