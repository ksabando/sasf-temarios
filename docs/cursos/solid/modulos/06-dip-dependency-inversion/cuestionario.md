### 2. [Investigar] ¿Cuál es la diferencia entre Inversion of Control (IoC) como principio general y DIP como principio de diseño? Investigá los orígenes de IoC (Martin Fowler, 2004 - "Inversion of Control Containers and the Dependency Injection Pattern") y explicá cómo el "Hollywood Principle" ("Don't call us, we'll call you") es IoC pero no necesariamente DIP.

**Respuesta**: Fowler popularizó IoC en 2004 describiendo cómo los frameworks invierten el flujo de control: tu código no controla el flujo principal; el framework lo hace. El "Hollywood Principle" es la personificación: no llames al framework; el framework te llamará a vos. Diferencia con DIP: **IoC** es sobre QUIÉN controla el flujo de ejecución (framework vs tu código). **DIP** es sobre DE QUÉ dependen tus módulos (abstracciones vs implementaciones). Ejemplos de IoC sin DIP: (1) Un servlet de Java donde `doGet()` es llamado por el contenedor (IoC: el contenedor controla el flujo), pero el servlet usa `new JdbcTemplate()` internamente (viola DIP). (2) Un callback de JavaScript donde `button.onClick = myFunction` — el navegador llama a tu función (IoC), pero `myFunction` puede depender de `document.getElementById()` directamente (sin abstracción). Ejemplo de DIP sin IoC: `Database db = DatabaseFactory.create("postgres")` — `db` es una interfaz (DIP), pero tu código instancia la fábrica y controla el flujo (no IoC). El ideal como en Spring: el contenedor IoC inyecta dependencias abstractas (IoC + DIP juntos). Fowler enfatiza que DI es una forma específica de IoC (la inyección de dependencias), pero IoC abarca más (patrones, eventos, callbacks).

**Por qué**: Fowler aclaró la confusión en su artículo de 2004: "Inversion of Control es un término genérico; Dependency Injection es la forma específica de IoC que nos interesa para desacoplar componentes". DIP es el principio de diseño que DI implementa.

### 3. [Investigar] ¿Cómo se aplica DIP en programación funcional? Investigá cómo los lenguajes funcionales logran inversión de dependencias mediante higher-order functions, type classes (Haskell/Scala), y el "Reader monad" pattern. ¿Son estos mecanismos más o menos poderosos que las interfaces en OOP?

**Respuesta**: En FP, DIP se implementa sin interfaces explícitas: (1) **Higher-order functions (HOF)**: en lugar de inyectar `Database` (interfaz) se inyecta `save: Order => IO[Unit]` (función). El componente de alto nivel recibe funciones que definen el comportamiento; el de bajo nivel provee funciones concretas. (2) **Type classes (Haskell)**: definen un contrato polimórfico sin herencia. `class Monad m` define el contrato; `instance Monad IO` lo implementa. El código de alto nivel trabaja con `Monad m => ...` (abstracción). Las implementaciones concretas son instancias de type class. (3) **Reader monad** (Scala Cats/ZIO, Haskell): `Reader[Database, A]` es una computación que requiere un `Database` para producir `A`. La dependencia se pasa implícitamente a través de la mónada. El componente de alto nivel retorna `Reader[Database, A]` sin ejecutar la dependencia. **Comparación con OOP**: Son MÁS poderosos en: (a) no requieren declarar interfaces explícitas (la función o type class es la abstracción), (b) la composición es natural (componer Reader monads, combinar type classes), (c) el polimorfismo paramétrico garantiza más propiedades que el polimorfismo por subtipado. Son MENOS poderosos en: (a) el descubrimiento de la API es más difícil (no hay una interfaz documentada, solo firmas de funciones dispersas), (b) el tooling de IDEs es más débil para type classes que para interfaces Java.

**Por qué**: Mark Seemann ("Dependency Injection in .NET") y Runar Bjarnason ("Functional Programming in Scala") exploran DIP en FP. La conclusión: FP logra DIP con menos ceremonias (sin interfaces explícitas) pero requiere más disciplina de documentación y tipos.

### 4. [Investigar] ¿Cómo funciona el Service Provider Interface (SPI) de Java y cómo se relaciona con DIP? Investigá java.util.ServiceLoader (Java 6+) y el mecanismo de providers en Java 9+ modules. ¿En qué se diferencia SPI de DI para implementar DIP?

**Respuesta**: Java SPI (ServiceLoader, desde Java 6) permite descubrir implementaciones de una interfaz en tiempo de ejecución escaneando el classpath. El módulo de alto nivel define una interfaz (ej. `java.sql.Driver`); los módulos de bajo nivel proveen implementaciones en `META-INF/services/`. La relación con DIP: SPI implementa DIP a nivel de plataforma porque: (1) El cliente depende solo de la interfaz (DIP). (2) El descubrimiento de implementaciones es automático — el cliente no conoce las implementaciones concretas (DIP). (3) Agregar una implementación es agregar un JAR al classpath sin modificar código (OCP + DIP). Diferencia con DI: **DI** asume que ALGUIEN (contenedor, fábrica) conoce todas las implementaciones y las inyecta explícitamente. **SPI** permite que las implementaciones se registren a sí mismas — el cliente consulta el ServiceLoader y obtiene todas las implementaciones disponibles sin que nadie las "inyecte" explícitamente. SPI es DIP con descubrimiento implícito; DI es DIP con inyección explícita. SPI se usa en JDBC (drivers de BD), SLF4J (logging), JAXP (parsing XML). En Java 9+, el `uses` en module-info consolida el SPI: el módulo cliente declara `uses DatabaseDriver` y los proveedores declaran `provides DatabaseDriver with MySQLDriver`.

**Por qué**: SPI es el mecanismo de extensión de la plataforma Java. Es DIP sin framework externo: el JDK mismo provee el mecanismo de inversión. La decisión SPI vs DI depende de quién controla el wiring: SPI = el proveedor se auto-registra; DI = un tercero (contenedor) cablea.

### 5. [Conectar] La clase menciona que DIP habilita la arquitectura hexagonal (Ports & Adapters). Investigá a fondo el trabajo original de Alistair Cockburn (2005) sobre Hexagonal Architecture y explicá cómo DIP es el "pegamento" que hace posible la inversión de dependencias entre el dominio y la infraestructura.

**Respuesta**: Alistair Cockburn propuso Hexagonal Architecture en 2005: la aplicación (dominio) está en el centro, y toda interacción externa pasa por "puertos" (interfaces) y "adaptadores" (implementaciones). DIP es el pegamento porque: (1) Los puertos SON las abstracciones de DIP definidas por el dominio: `OrderRepository`, `PaymentGateway`, `NotificationPort`. (2) Los adaptadores SON las implementaciones concretas de DIP: `MongoOrderRepository`, `StripePaymentGateway`, `EmailAdapter`. (3) La dependencia de código fuente va de los adaptadores hacia los puertos (DIP: los detalles dependen de las abstracciones). El dominio NUNCA importa un adaptador. Cockburn lo llamó "ports and adapters" porque los puertos definen el contrato (DIP: abstracción) y los adaptadores traducen (DIP: detalle). Lo que Martin llamó "Clean Architecture" (2012) es una refinación de Cockburn con DIP como principio central explícito: la "regla de dependencia" de Clean Architecture ("las dependencias de código fuente solo pueden apuntar hacia adentro") es DIP aplicado a todos los niveles. Sin DIP, Hexagonal Architecture colapsa: si el dominio importa `MongoOrderRepository` en lugar de depender de `OrderRepository`, el adaptador se filtra al centro.

**Por qué**: Cockburn y Martin convergieron independientemente en la misma arquitectura con diferentes nombres. Cockburn enfatizó la testeabilidad (cambiar adaptadores para tests); Martin enfatizó DIP como el mecanismo. Ambos reconocen que DIP es el principio que permite que el dominio sea independiente de la infraestructura.

### 6. [Conectar] Conectá DIP con el patrón "Dependency Injection" usando libraries en React. ¿Cómo el patrón de "InversifyJS" para TypeScript/React implementa IoC + DIP en frontend? Compará con el enfoque de Context API de la clase.

**Respuesta**: InversifyJS es un contenedor IoC para TypeScript que implementa DIP con decorators similares a Spring: `@injectable()` marca una clase como inyectable, `@inject(IMailService)` declara dependencias, y un contenedor define bindings entre interfaces e implementaciones. Comparación con Context API de la clase: **Context API** es DIP manual: cada componente lee del contexto (equivalente a Service Locator). Las dependencias son implícitas — no se declaran en el constructor. **InversifyJS** es DIP explícito: las dependencias se declaran en el constructor con `@inject`, y el contenedor las resuelve automáticamente. Ventajas de InversifyJS: (a) dependencias explícitas en firma (como constructor injection en Spring), (b) scope management (singleton, transient, request), (c) interceptors/middleware al estilo AOP, (d) resolución automática de árboles de dependencia. Desventajas: (a) más boilerplate que Context API (decorators, configuración de contenedor), (b) menos idiomático en React (la comunidad prefiere hooks + Context), (c) la resolución de dependencias es en runtime (decorators), no en build-time (como Dagger). Ambos cumplen DIP: el componente depende de `IMailService`, no de `SmtpMailService`. La elección depende de la escala: Context API para aplicaciones pequeñas/medianas (menos overhead), InversifyJS para aplicaciones grandes con muchas dependencias (mejor gestión de scopes y vida útil).

**Por qué**: InversifyJS (Remo Jansen, 2015) trae el patrón Spring al ecosistema TypeScript. Es la demostración de que DIP y IoC son independientes del lenguaje: si tenés interfaces y constructores, podés implementar DIP con un contenedor.

### 7. [Conectar] Relacioná DIP con el concepto de "Test Doubles" (Gerard Meszaros, "xUnit Test Patterns", 2007). ¿Por qué sin DIP no podés usar stubs, mocks o fakes efectivamente? Explicá cómo cada tipo de test double requiere un nivel diferente de DIP.

**Respuesta**: Meszaros clasificó test doubles en: **Dummy** (no se usa), **Stub** (retorna valores prefijados), **Spy** (registra llamadas), **Mock** (verifica expectativas), **Fake** (implementación alternativa ligera, ej. DB en memoria). Sin DIP, ninguno es viable porque: la clase bajo test instancia directamente `new MySQLDatabase()`. No hay punto de inyección para insertar el test double. Con DIP, la clase recibe `Database` (interfaz) por constructor: se puede inyectar cualquier test double. Niveles de DIP requeridos: **Stub** solo necesita que la dependencia sea una interfaz (nivel mínimo de DIP: una interfaz con un método). **Mock** necesita interfaz para que Mockito pueda generar el proxy. **Fake** necesita interfaz + una segunda implementación (nivel medio de DIP: abstracción con al menos dos implementaciones). **Spy** necesita lo mismo que mock. Dummy no requiere DIP (no se usa) pero se beneficia de él (inyectar null en lugar de instanciar). Conclusión: DIP es el habilitador universal de test doubles. Un sistema sin DIP es un sistema sin test doubles efectivos, y por lo tanto sin pruebas unitarias rápidas. Meszaros implícitamente asume DIP porque todos sus patrones de test doubles requieren que la dependencia sea inyectable.

**Por qué**: La conexión Meszaros-Martin: los test doubles son la herramienta práctica; DIP es el principio que los hace posibles. Sin DIP, cada prueba es de integración (lenta, frágil).

### 8. [Cuestionar] ¿Es DIP siempre beneficioso o puede llevar a una "arquitectura de cebolla podrida"? Investigá críticas sobre sistemas donde cada clase tiene una interfaz, cada método tiene una abstracción, y el grafo de dependencias es tan complejo que entender el flujo requiere herramientas de visualización. ¿Dónde está el límite de la inversión?

**Respuesta**: Críticos como John Ousterhout ("A Philosophy of Software Design") y Yegor Bugayenko señalan que DIP mal aplicado produce: (1) **Indirección innecesaria**: cada clase tiene una interfaz correspondiente que solo existe para cumplir DIP, no porque haya múltiples implementaciones. Si `OrderService` es la ÚNICA implementación de `IOrderService`, la interfaz es ruido. Ousterhout: "los módulos profundos tienen interfaces pequeñas e implementaciones complejas". El anti-patrón DIP es "interfaces grandes e implementaciones triviales" — cada método de `IOrderService` delega a `OrderService`. (2) **Arquitectura de cebolla podrida**: cuando las capas de abstracción se multiplican (Controller → IOrderService → IOrderRepository → IDatabase), seguir el flujo requiere abrir 8 archivos. El costo cognitivo supera el beneficio de desacoplamiento. (3) **YAGNI violado**: abstracciones creadas para cambios hipotéticos que nunca ocurren. El límite: DIP debe aplicarse a dependencias VOLÁTILES (BD, APIs externas, servicios cloud) pero no a dependencias ESTABLES (value objects, utilidades del lenguaje, lógica de dominio interna que es inherentemente acoplada). La regla: solo invertí dependencias que: (a) tienen al menos DOS implementaciones en producción, o (b) son de infraestructura (BD, mensajería, HTTP), o (c) impiden el testing rápido. Para todo lo demás, el acoplamiento directo es más simple y no tiene costo.

**Por qué**: Ousterhout (2018) dedica un capítulo entero a "Define Errors Out of Existence" y "Design it Twice" donde argumenta contra las abstracciones prematuras. Martin coincide parcialmente: DIP es para dependencias volátiles, no para todo.

### 9. [Cuestionar] ¿DIP o "Service Locator"? Martin Fowler (2004) argumentó que Service Locator es un anti-patrón comparado con Dependency Injection. Pero frameworks como Android (con Hilt/Dagger) y algunos sistemas legacy usan Service Locator exitosamente. ¿Es realmente un anti-patrón o una alternativa válida en ciertos contextos?

**Respuesta**: Fowler en 2004 describió Service Locator como la alternativa a DI donde el objeto pide sus dependencias a un registro (`ServiceLocator.resolve(IDatabase.class)`) en lugar de recibirlas por constructor. Críticas de Fowler: (1) Dependencias ocultas: no podés saber qué necesita una clase mirando su constructor — tenés que leer su cuerpo. (2) Acoplamiento al Service Locator: todas las clases dependen de la clase `ServiceLocator`. (3) Dificultad de testing: necesitás configurar el Service Locator global antes de cada test. **Defensa del Service Locator**: (1) En Android, Hilt/Dagger generan código que actúa como Service Locator compilado, no runtime — no hay penalidad de performance. (2) Para sistemas legacy donde no se puede refactorizar todo a constructor injection, Service Locator es un paso intermedio pragmático. (3) En lenguajes sin contenedor IoC (C, Go), Service Locator es la única opción. (4) Kevlin Henney argumenta que Service Locator es DIP válido si el locator retorna interfaces: el cliente sigue dependiendo de la abstracción; solo cambia el mecanismo de obtención. **Conclusión**: Service Locator no es inherentemente malo; es inferior a DI en testabilidad y transparencia. Pero en contextos donde DI no es viable (ausencia de framework, limitaciones del lenguaje), Service Locator con interfaz es una aplicación válida de DIP (aunque subóptima).

**Por qué**: Fowler mismo matizó su posición: "Service Locator is not inherently evil, but it has downsides that DI avoids". La industria mobile (Android con Dagger/Hilt que genera Service Locators en compile-time) demostró que la versión compilada del patrón resuelve las principales objeciones.

### 10. [Cuestionar] ¿Es DIP el principio más "costoso" de SOLID? Investigá el trade-off entre inversión de dependencias y performance/carga cognitiva. ¿Hay dominios (ej. sistemas embebidos, videojuegos, high-frequency trading) donde DIP activamente perjudica?

**Respuesta**: DIP tiene costos reales: (1) **Performance**: cada llamada por interfaz en Java implica despacho virtual (vtable lookup). En sistemas de alta frecuencia (HFT, trading), la diferencia entre llamado directo y llamado virtual puede ser inaceptable. (2) **Memoria**: objetos inyectados + proxies + contenedor IoC consumen heap. (3) **Carga cognitiva**: la indirección hace que el debugging sea más difícil (stack traces más profundas, necesidad de tooling de visualización de dependencias). (4) **Build time**: sistemas con miles de interfaces compilan más lento. Dominios donde DIP perjudica: **Videojuegos**: ECS (Entity Component Systems) evitan herencia/interfaces por performance. En Unity, `GameObject.GetComponent<T>()` es más costoso que acceso directo. Los motores de juego optimizan para data locality (cache-friendly), no para desacoplamiento. **Sistemas embebidos**: con restricciones de memoria (64KB RAM), cada vtable es overhead. **HFT**: cada nanosegundo cuenta; la indirección de interfaz es inaceptable. Robert Nystrom ("Game Programming Patterns", 2014) y Mike Acton (Data-Oriented Design) argumentan que SOLID asume recursos abundantes; en sistemas con restricciones extremas, la simplicidad y performance dominan sobre la extensibilidad. Martin reconoce esto: SOLID es para software empresarial con vida útil larga y requisitos cambiantes, no para todo el software.

**Por qué**: Martin en Clean Architecture aclara que SOLID es para sistemas donde el costo de mantenimiento domina sobre el costo de hardware. En sistemas donde la performance es el requisito principal, DIP es un lujo que no todos pueden pagar.
